## 1. CPU 与 GPU 的区别

**底层构成**：CPU与GPU底层均由晶体管组成逻辑门，这一层完全相同。区别在于晶体管数量的分配方式。

**CPU**：晶体管主要用于构建控制逻辑——ALU（算术运算电路）、分支预测器（预判if/else分支）、乱序执行单元（调整指令执行顺序）、多级缓存（L1/L2，每核心独享）。这些电路占用大量芯片面积，导致核心数量少（几十个）。

**GPU**：省去复杂控制逻辑，仅保留基础ALU，将省下的晶体管用于复制大量计算单元（如A100有8192个CUDA Core）。

**判断GPU是否适用的标准**：任务能否拆分为大量**相互独立**的小任务，而非任务本身"简单"或"复杂"。
- 判断成立的例子：人脸识别（复杂但可拆分为独立矩阵运算）适合GPU；斐波那契数列计算（简单但存在强顺序依赖）不适合GPU。

## 2. SM、CUDA Core、Tensor Core

### 2.1 线程（Thread）

**定义**：线程不是物理实体，而是"同一份GPU代码的一次独立执行"，通过唯一编号区分其处理的数据。

**示例**：对1,048,576个像素各加10，代码只写一份：
```
编号 = 我的线程编号
像素[编号] = 像素[编号] + 10
```
该代码被执行1,048,576次，每次执行（对应不同编号）构成一个线程。

**GPU线程与OS线程的区别**：

| 维度 | OS线程 | GPU线程 |
|---|---|---|
| 创建开销 | 较大，数量克制（几个至几千个） | 几乎无开销，可达百万级 |
| 执行逻辑 | 各线程可执行完全不同的代码 | 同一份代码，仅处理数据不同 |
| 调度单位 | 单个线程独立调度 | 32个线程打包成warp统一调度 |
| 数量关系 | 线程数远小于任务数 | 线程数等于甚至超过数据量 |

### 2.2 Warp

**定义**：32个线程固定打包成一组，是硬件调度的最小单位。同一warp的32个线程必须在同一时刻执行完全相同的指令（SIMT：Single Instruction, Multiple Threads），各自作用于不同数据。

**设计原因**：若调度系统单独管理百万级线程，控制电路会极其复杂。按warp打包后，调度器只需对"一组"下达一次指令，简化了调度电路，节省的硬件面积用于增加计算单元数量。

### 2.3 Block

**定义**：程序员指定大小（如256、512、1024个线程）和数量的一组线程，内部按32个拆分为若干warp。Block大小不能超过硬件规定的上限（如单Block最多1024线程）。

**核心规则**：一个Block必须整体分配到同一个SM，不能被拆分到多个SM。

**原因**：Block内线程被设计为可共享同一块共享内存以协作计算。若Block被拆分到SM 0和SM 1，SM 1无法访问SM 0的共享内存（两者物理隔离，无硬件通路），会导致数据依赖关系断裂、程序逻辑出错。这是由共享内存机制决定的硬件约束，而非人为设定的限制。

不同Block之间因设计上不共享数据，可自由分散到不同SM。

### 2.4 Grid

一次任务中，全部Block的总集合。

### 2.5 SM（Streaming Multiprocessor）

物理硬件模块，是GPU芯片调度任务的基本单位。以A100为例：GPU共128个SM，每个SM包含64个CUDA Core、4个Tensor Core、65536个32-bit寄存器、约192KB共享内存及一个调度器。

### 2.6 寄存器 vs 共享内存

| | 寄存器 | 共享内存 |
|---|---|---|
| 归属 | 按**线程**动态分配，非物理绑定给某个CUDA Core；线程被调度到某Core执行时，就近读取其名下分配的寄存器 | 同一SM内所有线程共用，SM外不可见 |
| 容量（A100） | 65536个/SM | 约192KB/SM |
| 速度 | 最快 | 比寄存器慢，但远快于显存 |
| 用途 | 存储线程私有的临时计算数据 | 存储同SM内多线程需复用的数据，避免反复访问显存 |

范围关系：寄存器（单线程可见）⊂ 共享内存（单SM可见）⊂ 显存（全GPU可见）。寄存器与共享内存均属于"片上存储"，物理位置紧邻计算单元；显存则在芯片外部。

### 2.7 CUDA Core vs Tensor Core

**CUDA Core**：执行标量运算（一次处理一个数的加减乘除/FMA）。

**Tensor Core**：专用电路，一次性完成固定规模的矩阵乘加（D = A×B + C）。硬件底层实际执行4×4矩阵乘加；FP16精度下常见编程tile为16×16×16；Hopper架构单指令可处理64×64×16。真实模型中的大矩阵，通过拆分成多个小tile循环调用Tensor Core、累加结果完成，而非一次性处理整个大矩阵。

**数量比例（A100，每SM）**：CUDA Core : Tensor Core = 64 : 4 = 16 : 1。

**运算速度对比示例**（4×4矩阵乘加，D=A×B+C）：
- 16个CUDA Core并行：16个格子并行计算，但每个格子内部需4次FMA串行累加，共需4个时钟周期。
- 1个Tensor Core：硬件电路直接并行完成64次FMA，仅需1个周期。

**协作方式**：同一warp在不同执行阶段，可交替使用CUDA Core（标量指令）和Tensor Core（矩阵乘加指令），两者是流水线式接力关系，非互斥。

**必须使用CUDA Core（而非Tensor Core）的场景**：激活函数（ReLU等，逐元素非线性变换）、归一化（LayerNorm等）、逐元素加法（残差连接、bias）、矩阵维度或精度不满足Tensor Core硬件对齐要求时。

### 2.8 Block在SM上的调度机制

**SM能同时驻留多少Block**：由以下三项资源上限共同决定，取最小值——
1. 寄存器总量 ÷ 每Block所需寄存器数
2. 共享内存总量 ÷ 每Block所需共享内存
3. 硬件规定的驻留warp数上限 ÷ 每Block的warp数

**调度优先顺序**：
1. **分散**：优先让尽可能多的SM各分到至少1个Block。
2. **填满**：分散完毕后若仍有剩余Block、且某些SM有空余资源，才继续向这些SM追加Block。
3. 若所有SM均无空位，剩余Block留在全局待分配队列中，待某SM释放资源后立即补位。

**延迟隐藏（Latency Hiding）机制**：一个SM同一瞬间仅能有2个warp的线程真正占用CUDA Core执行（64个CUDA Core ÷ 32），但可同时驻留远超过2个warp（如64个）。当某warp因等待显存数据而阻塞时，调度器立即切换执行另一个已就绪的warp，使CUDA Core几乎不空闲。

**该机制生效的前提**：SM内驻留的warp数量需足够多、来源足够多样（跨越多个Block）。若SM只驻留单一Block，一旦该Block的warp集体阻塞，将无备选项可用。

**Block总数需远超SM总数的原因**：若Block总数仅"刚好够分"（如130个Block对128个SM），"分散"步骤几乎耗尽全部Block，导致绝大多数SM仅驻留1个Block，缺乏备选warp来源，延迟隐藏机制难以发挥作用；同时容易造成各SM完成任务的时间不均衡。Block总数远超SM数时，"填满"步骤才能充分执行，使每个SM都拥有充足、多样的warp来源。

**排队范围的边界**：不同Block之间可（通常会）分散到不同SM实现跨SM并行；同一Block内的warp则永远绑定在其被分配到的那一个SM内部排队，无法借用其他空闲SM的资源。Block设计过大可能导致大量warp被迫在单一SM内排队，造成并行度不足。

## 3. GPU显存和显存带宽

**显存（Global Memory）**：GPU芯片外部、板载的大容量存储器，所有SM均可访问，容量远大于片上存储（寄存器/共享内存），但访问速度更慢。

**显存带宽**：显存与计算单元之间数据传输的**理论峰值速率**（单位GB/s），而非实际发生的传输速度。理论峰值是硬件设计决定的固定上限，实际数据搬运速度受任务特性影响，通常低于该峰值。

**显存容量与显存带宽是两个独立指标**：容量（GB）回答"能存多少"，带宽（GB/s）回答"传输多快"，二者不能互相推断。判断GPU是否满足任务需求时，容量不足会导致任务直接无法运行，这是比带宽更优先的硬约束；若容量足够，再比较带宽对任务速度的影响。

## 4. GPU utilization 的统计含义

**统计粒度**：SM级别。

**统计逻辑**：在采样周期内（通常1/6秒到1秒），只要至少有一个SM上有kernel在执行，该周期即被记为"忙碌"。这是**二元判断**（有无活跃kernel），不考虑该SM内部实际使用了多少CUDA Core、warp是否只是在等待而非真正计算。

**验证案例**：在128个SM的GPU上，仅用1个SM运行一个不含实际计算的死循环kernel，其余127个SM完全空闲，`nvidia-smi`报告的GPU-Util仍为100%；而更细粒度的监控工具显示SM occupancy低于20%。

## 5. 为什么GPU利用率100%不代表性能正常

常见的"高利用率但性能异常"场景：

1. **显存带宽瓶颈**：计算量小但需频繁读取显存数据，SM大部分时间在等待数据搬运而非真正计算，但只要SM被kernel占用即记为忙碌。
2. **Batch size过小**：任务仅创建少量Block，只有少数SM分到任务，其余大量SM空闲，但只要有活跃SM即显示100%。
3. **PCIe传输瓶颈**：GPU等待CPU通过PCIe传输数据，若采样点恰好落在GPU正处理已到达数据的瞬间，会被误判为忙碌，但整体吞吐受限于传输速度。

**nvidia-smi dmon**：可持续、周期性输出多项指标。其中`sm`列即GPU utilization；`mem`列为显存利用率，同样是"时间占比"统计（显存被读写的时间百分比），而非"显存带宽实际用了百分之多少"。

- 使用条件：需在真实负载运行时执行，并持续观察多个周期，而非依赖单次瞬时值（负载通常存在波动）。
- 能支持的结论：可观察指标走势，作为进一步排查方向的线索。
- 不能支持的结论：不能证明GPU算力被充分利用；不能区分SM是在真正计算还是在等待；不能单独定位瓶颈具体位置（需结合更多信息）。

## 6. GPU时钟频率

**定义**：芯片内部时钟信号每秒钟产生的"周期（cycle）"次数，单位MHz/GHz。1个周期时长 = 1秒 ÷ 频率（如2GHz对应周期时长0.5纳秒）。

**两类独立时钟**：
- **SM Clock**：驱动CUDA Core/Tensor Core等计算单元。
- **Memory Clock**：驱动显存读写。

两者物理上独立，可各自变化，无需同步。

**周期长度的物理依据**：周期时长由电路中信号传播延迟最长的那个阶段决定，以保证每个周期内该完成的电路操作能够完整、稳定地执行完毕，不会因周期过短导致信号未稳定即被读取而出错。

**流水线（Pipeline）**：若单次完整操作（如一次FMA）无法在1个周期内完成，可将其拆分为多个阶段，由不同电路模块负责，多个操作在流水线的不同阶段同时被处理（错峰重叠）。这样虽然单个操作从开始到结束仍需跨越多个周期（延迟，latency），但通过多操作重叠，整体上仍可实现"每周期产出一个结果"（吞吐量，throughput）。

**频率提升的物理限制**：受晶体管开关速度和信号传播速度的物理极限约束，无法无限提升。

## 7. GPU功耗及其单位W

**定义**：单位时间内消耗的电能，单位瓦特（W）= 焦耳/秒。

**功耗来源**：
- **动态功耗**：晶体管开关状态切换时消耗的电能，与频率直接相关（频率越高，单位时间内切换次数越多）。
- **静态功耗**：芯片通电即存在的微弱漏电，相对固定，占比通常较小。

**CPU同样存在功耗**（如TDP指标），但GPU因同时有大量计算单元在高频率下切换，满载功耗通常远高于同代CPU。

**功耗与性能的关系**：功耗高不代表性能好。功耗仅反映"耗电速率/晶体管切换活跃程度"，不反映这些切换是否转化为有效计算产出。可能存在功耗不低但在做无效运算（如空转）、或旧架构能效比低（功耗高但实际算力产出不如新架构）的情况。判断性能应看单位功耗的有效产出（能效比），而非功耗数值本身。

## 8. 利用率、功耗、频率、温度之间的关系

**通常成立的因果链**：
```
Utilization ↑ → 频率维持高位/尝试提升 → 功耗 ↑（晶体管切换更频繁）
→ 温度 ↑（电能转化为热能）→ 若温度触及安全上限，强制降低频率（保护机制）
→ 功耗与温度回落，形成动态循环
```

**必然成立**：温度达到硬件安全上限时，GPU必然自动降频，这是硬件/固件层面强制执行、不可被软件绕过的保护机制。

**不必然成立**：并非所有utilization高的场景都会导致功耗、温度同步大幅上升——例如仅1个SM空转的极端场景，utilization为100%，但实际参与切换的晶体管数量很少，功耗和温度的上升幅度远小于全部SM满载的场景。因此utilization相同不代表功耗、温度走势必然相似。

## 9. Power Limit、功耗墙、温度墙

**Power Limit**：为GPU设定的最大允许功耗上限（单位W），可通过如`nvidia-smi -pl`在硬件允许范围内调整，并非固定不变的物理极限。

**功耗墙**：实际功耗达到Power Limit时触发的保护机制，通过降低频率使功耗回落到限制线以下。

**温度墙**：核心温度达到厂商设定的安全上限（通常约80~90°C，因型号而异）时触发的保护机制，同样通过降频减少发热。

**两者关系**：功耗墙与温度墙是两条独立、并行的监控机制，哪一条先被触碰即由哪一条先触发降频。散热良好的环境中通常功耗墙先触发；散热不良的环境中通常温度墙先触发。

**必然性**：只要功耗或温度任一项达到设定上限，GPU必然降频，此为硬件/固件强制执行的保护逻辑，软件层面无法阻止（只能提前调整Power Limit这一可配置阈值本身）。

**反向推论**：若GPU未发生降频，说明功耗墙和温度墙均未被触碰。

## 10. P0、P1等 P-State

**定义**：NVIDIA GPU定义的一套离散预设性能状态等级（P0至P15，不同代际支持档位数可能不同）。编号越小，性能、频率、功耗越高；P0为最高性能档位。

**与频率的本质区别**：频率是连续数值（可取任意具体值，如1.3GHz、1.35GHz），P-State是有限的离散预设档位（不存在"P3.5"这类中间值）。P-State可理解为"频率+功耗"打包在一起的组合状态，GPU根据当前负载、功耗、温度状况整体切换到某个档位，而非先单独调节频率、再对应到某个P-State。

**与utilization的关系**：utilization高时GPU通常倾向维持在P0，但这不是绝对的——若触碰功耗墙或温度墙，即使任务负载仍然很高（utilization显示100%），GPU也可能被迫切换到编号更大（性能更低）的P-State。二者是不同维度的信息，不能仅凭utilization断定当前所处的P-State，需单独查看该字段确认。
