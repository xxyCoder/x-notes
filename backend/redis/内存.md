## 知识点4：键的过期机制

### 4.1 TTL 存储位置

每个 `redisDb` 结构体内有两个独立字典：

```c
typedef struct redisDb {
    dict *dict;      // 主键空间：key -> value(robj)
    dict *expires;   // 过期字典：key -> 过期时间戳(long long, 毫秒)
    ...
} redisDb;
```

- 执行 `SET mykey "hello"` + `EXPIRE mykey 100`，效果是：
  - `db->dict["mykey"] -> robj("hello")`
  - `db->expires["mykey"] -> 当前时间+100000ms`
- 两个字典的 key 指针共享，不重复存字符串。
- 没设 TTL 的 key，在 `expires` 字典里根本没有对应 entry，不产生额外内存开销。
- **关键认知**：设置 TTL 只是"记了个截止时间"，Redis 不会为每个 key 单独设定时器/回调，一切都靠"反复检查现在几点、和记录的时间比一比"。

### 4.2 惰性删除（被动检查）

- 触发点：几乎所有读写命令访问 key 之前，都会调用 `expireIfNeeded()` 检查。
- 逻辑：查 `db->expires`，若当前时间 > 记录的过期时间 → 判定已过期 → 立即 `dbDelete`（同时删 `dict` 和 `expires`）→ 返回 nil，并向 AOF 追加 DEL、向从库传播 DEL。
- **缺陷**：如果一个 key 设了 TTL 后再未被访问，惰性删除永远不会触发它，会一直占用内存，是典型的"僵尸 key"来源。

### 4.3 主动删除·慢周期

- 挂在 `serverCron`，由 `hz` 决定频率，默认 `hz=10`，即每 100ms 触发一次。
- **单轮采样逻辑**：
  - 每次先判断该 db 是否为空或过期 key 密度过低（<1%），是则直接跳过（这个 break 发生在 `iteration++` 之前）。
  - 每轮从 `db->expires` 随机抽取 20 个 key（`ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP`），逐个检查是否过期，过期就删。这 20 个的检查过程中**不检查时钟**，一定跑完。
- **两种退出条件（必须分清）**：

| 退出方式 | 判断依据 | 结果 |
|---|---|---|
| 正常收工 | 本轮删除数 ≤ 25%采样数（即 ≤5个/20个） | 说明过期密度已经低了，主动结束 |
| 超时中断 | 每完成16轮抽样才检查一次时钟（`iteration & 0xf == 0`），发现耗时超过预算 | 强制break，不管数据库里还有多少过期key没处理 |

- 时间预算：慢周期 25ms（100ms周期的25%）。

### 4.4 主动删除·快周期

- 挂在 `beforeSleep`（每次事件循环准备进入 `epoll_wait` 前）。
- **触发条件（两条限流规则，缺一不可）**：
  1. 只有上一次慢周期是"超时中断"退出的，快周期才会真正执行清理；若慢周期都能正常收工，快周期直接跳过。
  2. 两次快周期之间至少间隔 2ms。
- 时间预算：1ms，内部逻辑（抽样-删除-判断阈值）与慢周期完全一致，只是换了个时间上限传参。

### 4.5 为什么时间上限是"软上限"——两层原因

**原因A：检查粒度问题**
时钟检查不是每轮都做，是每 16 轮抽样（最多320个key）才检查一次。正常情况下这320次内存比较很快，偏差不大。

**原因B：单个key删除代价不可控**
如果抽到的 key 是一个几百万元素的大集合，同步删除本身可能耗费数毫秒，这个耗时会被算进"当前这一轮"，在下一次16的倍数检查点到达前，时钟根本没机会介入打断。这也是后续引入 **lazy free**（异步释放大key内存，主线程只做O(1)摘除）的动因。

**结论**：25ms/1ms 不是硬保证，只是两次检查点之间的近似预算。

### 4.6 超时会不会累积延迟——自我修正 vs 真正滚雪球

- **日常不会累积**：`serverCron` 每次执行完，返回"下次请在多少毫秒后调用我"，这个基准点是"刚执行完的这一刻"，不是绝对时间格子。所以一次超时只会把**下一次**往后推，不会转嫁给第三次、第四次——每次独立计算，不背历史债。
- **真正会恶化的场景**：如果过期key产生速度持续、稳定地超过清理能力，不会无限累积延迟，而是**卡在一个更差的稳定态**（清理任务持续吃满25% CPU预算）。若这种压力叠加触发了内存淘汰（响应速率<到达速率→积压→更多内存压力→更多清理/淘汰开销→响应更慢），才会形成真正的正反馈雪球。

### 4.7 主从场景下的不对称性

- **主库**：正常执行惰性删除+慢/快周期，检测到过期就删除，并通过传播 DEL 命令同步给所有从库。
- **从库**：自己不会主动删除过期key，必须等主库的 DEL 命令到达才真正物理移除。但从 Redis 3.2 起，从库处理读请求时会用**自己本地的 `expires` 时间戳和自己本地时钟**做比较，若判定逻辑上已过期，会对客户端返回 nil（即使底层数据还没被物理删除）。
- **设计目的**：避免"主库还没通知、从库先自己删了"造成主从数据不一致（例如故障切换后数据状态对不上）。
- **异常排查**：若 3.2+ 版本的从库仍返回了"应该已过期"的真实内容（不是nil），最可能的原因是**主从系统时钟不同步（clock skew）**——从库用自己偏慢的本地时钟去跟过期时间戳比较，会得出"还没过期"的错误结论。单纯的复制延迟不足以解释这个现象，因为从库的nil判断不依赖DEL是否到达。

## 知识点5：内存淘汰策略（maxmemory-policy）

### 5.1 触发时机

- 不是后台定时任务，而是**每次执行可能增加内存占用的命令前**（带 `CMD_DENYOOM` 标记的命令，如SET/LPUSH/HSET），先检查内存是否超过 `maxmemory`。
- 超过则触发淘汰循环；淘汰后仍不够、且策略是 `noeviction` 或命令带DENYOOM标记，直接拒绝命令，返回OOM错误。
- 纯读命令（GET）不会触发这个检查。

### 5.2 八种策略

| 策略 | 候选范围 | 淘汰依据 |
|---|---|---|
| noeviction | 不淘汰 | 直接拒绝写命令 |
| allkeys-lru / volatile-lru | 所有key / 仅TTL key | 最久未被访问 |
| allkeys-lfu / volatile-lfu | 所有key / 仅TTL key | 访问频率最低 |
| allkeys-random / volatile-random | 所有key / 仅TTL key | 随机 |
| volatile-ttl | 仅TTL key | 剩余TTL最短 |

**生产坑**：若选了`volatile-*`策略但业务中没有任何key设置TTL，`expires`字典为空，淘汰会直接失败，效果等同于`noeviction`——写入照样会被拒绝。

### 5.3 统一设计哲学：绝不精确遍历，全部靠"抽样+候选池"近似

这是贯穿LRU/LFU/TTL三种策略的核心机制，流程完全一致：

```
1. 从候选范围随机抽5个key（默认 maxmemory-samples=5）
2. 计算这5个key各自的"指标值"（LRU=idle秒数；LFU=热度低；TTL=剩余时间）
3. 尝试插入固定16格的候选池（按指标排序）：
   - 池子没满：直接插入
   - 池子满了：只有新key"更该被淘汰"，才替换掉池子里"最不该淘汰"的那个
4. 从候选池中挑出"最该淘汰"的那个，立即删除
   （注意：不需要等池子攒满16个才开始淘汰，抽完一轮5个就可以淘汰一个）
5. 检查内存是否达标：
   - 达标：结束
   - 不达标：回到第1步，继续抽5个塞入同一个候选池，继续淘汰
   循环直至达标
```

**⚠️ 核心反直觉特性——候选池数据是"定住的"（staleness）**：
一个key的候选池记录只在"被抽样那一瞬间"计算一次，之后**不会被自动刷新或跟踪实时状态**。除非：①该key再次被抽样命中并重新计算插入；②它被淘汰；③它被更极端的新样本顶替出局——否则无论这个key在真实世界里变得多热或多冷，候选池里的记录都不会自己感知到。

> **典型陷阱案例**：一个key（如 `hot:product:{id}`）在刚创建、还没被大量访问的瞬间恰好被抽样命中，此时idle值不高但也不算低；一旦被塞入候选池，这个idle值就此"定格"。之后即使该key被疯狂高频访问（真实idle接近0），候选池里的陈旧记录不会自动更新，它会一直"卡"在池子里，直到某轮淘汰循环转到它，被当成"很老的key"误删——尽管此刻它实际上是全场访问最频繁的key之一。这是LRU策略"用一次不走运的采样时机定终身"的根本缺陷来源。

### 5.4 LRU 具体实现

**存储**：复用 `RedisObject` 的24位 `lru` 字段，记录"服务器启动以来经过了多少整秒"（分辨率=1秒，即同一秒内不管访问多少次都是同一个值）。由 `server.lruclock` 维护，后台约每100ms刷新。

**为什么只精确到秒**：24位最多表示约1677万，精确到毫秒很快溢出；精确到秒可连续记录约194天才回绕，对"多久没人碰"这个判断目的完全够用。

**计算**：`idle = server.lruclock - robj->lru`，idle越大越该被淘汰，候选池按idle排序，取最大者删除。

**溢出处理**：194天后lru字段会回绕，Redis内部有修正逻辑，若算出idle为负数则视为回绕并修正，不会误判成"刚访问过"。

### 5.5 LFU 具体实现

**存储**：同样复用24位字段，拆成两半：
- 高16位：`ldt`（Last Decrement Time），记录"上次热度衰减发生在第几分钟"
- 低8位：`counter`，热度计数器，取值0~255

**递增机制（对数概率递增）**：
```c
uint8_t LFULogIncr(uint8_t counter) {
    if (counter == 255) return 255;
    double r = (double)rand()/RAND_MAX;
    double baseval = counter - LFU_INIT_VAL;  // LFU_INIT_VAL默认5
    if (baseval < 0) baseval = 0;
    double p = 1.0/(baseval*server.lfu_log_factor+1);  // lfu_log_factor默认10
    if (r < p) counter++;
    return counter;
}
```
counter越小时越容易涨；counter已经很大时，涨1点的概率变得很小，需访问很多次才有机会涨一次。这样8位空间能粗略映射几十万次真实访问的量级差异。

**衰减机制（"懒惰衰减"，不是后台任务）**：
Redis **没有**专门的后台任务去定期遍历所有key做降温。只有当一个key**真的被碰到**（被访问或被抽样命中）时，才会顺便计算该退多少温：
```c
unsigned long num_periods = LFUTimeElapsed(ldt) / server.lfu_decay_time;
counter = (num_periods > counter) ? 0 : counter - num_periods;
```
`lfu-decay-time` 默认1（分钟），即**每过1分钟没被访问，counter就掉1点**。

**数值示例**：counter=255（打满），若之后完全没访问，255÷1点/分钟＝255分钟≈4小时15分钟即可完全归零。这意味着一个曾经爆火但访问有间隔的key，可能在几小时内就被判定为"冷"而遭淘汰，比很多人以为的"天级"衰减快得多——如果业务有周期性流量（例如商品间隔数天有小高峰），默认衰减速度可能过于激进，需要调大`lfu-decay-time`或调整`lfu-log-factor`。

**为什么初始值是5而不是0**：`LFU_INIT_VAL=5`让新key有一个基础热度，避免刚创建就在下一轮抽样中被误判为"最冷"而立刻被淘汰。

### 5.6 LRU vs LFU 的本质区别（抗陈旧数据能力）

- LRU的指标（idle）是**瞬时的、一次性快照**，容易被候选池的陈旧记录"钉死"。
- LFU的指标（热度计数器）是**累积的**，需要持续访问才能改变，一次不走运的采样时机不会永久定终身，因为持续的真实访问会很快把计数器顶回高位并覆盖旧记录。

### 5.7 volatile-ttl

- 同样是抽样+候选池机制，**不是精确扫描全部TTL key找最短的那个**。若全局意义上剩余时间最短的key运气不好没被抽到，会等后续某轮抽样命中才处理——但因为淘汰循环持续进行直至达标，这种"漏网"通常只是稍晚处理，不会有明显影响。

### 5.8 random策略

不看任何指标，直接随机挑候选范围内的key删除，牺牲精确度换取无需维护候选池/计算指标的开销。

## 知识点6：内存碎片与优化

### 6.1 两个基础数字

```
used_memory       # Redis自己统计"数据结构实际使用的内存"
used_memory_rss   # 操作系统层面，进程实际占用的物理内存(RSS)
mem_fragmentation_ratio = used_memory_rss / used_memory
```

- 经验阈值：超过1.5通常视为警戒信号；健康状态接近1.0~1.2。
- **反直觉边界情况**：若数据量正在整体减少（如刚做完大规模删除），`used_memory`（分母）缩小但操作系统不一定立刻收回物理页，此时比值会显得很高，不代表当前配置有问题，只是"曾经用过的内存还没被真正归还"。`used_memory_peak`可用来验证这一点——若`used_memory_rss`接近`used_memory_peak`，说明这个差距很可能只是历史遗留囤积，不是当前异常。

### 6.2 碎片分层模型（"仓库三层打包"类比）

| 层级 | 类比 | 字段 | 含义 |
|---|---|---|---|
| 真实数据 | 货物实际重量 | （无直接字段，对应`dataset.bytes`） | 应用层真正需要的数据量 |
| 第一层 | 账本记的发出箱子总重量 | `allocator.allocated` | jemalloc分配出去的总字节（按固定档位"装箱"，比真实数据略大） |
| 第二层 | 仓库里正被占用的货架总面积 | `allocator.active` | 分配器认为"活跃"的内存页（按整页占用，即使页内有空隙也整页算占用） |
| 第三层 | 向房东租的总地皮面积 | `allocator.resident` | 操作系统眼中实际占用的物理内存（jemalloc释放后不一定立刻归还给OS，会囤积） |

**正确公式（务必注意方向，除数是"前一层"）**：
```
allocator-fragmentation.ratio = allocator.active / allocator.allocated   # 衡量"内部碎片"
allocator-rss.ratio           = allocator.resident / allocator.active     # 衡量"囤积未归还"
```
两个比值都应该 ≥1，且越大浪费越严重；写反方向（分子分母颠倒）会导致比值恒小于1，失去衡量意义。

**内部碎片 vs 外部碎片的本质**：
- **内部碎片**：jemalloc按固定档位分配（8/16/32...一路到接近14KB，超过14KB则按大对象单独处理），实际请求字节数比档位小时，多出的部分被浪费。例如4097字节的对象被塞进下一档位，可能浪费近一半空间。
- **外部碎片**：随着key被创建、修改（尤其是可变长度的value，如反复APPEND/SETRANGE）、删除或过期，分配器留下分散的、大小不规则、无法被后续请求复用的空闲空间。这种情况常见于：key大小不固定、工作负载存在大批量删除/过期、频繁更新导致value长度变化的场景。**这两种业务行为（改大小、删key）共同制造的是同一类"外部碎片"现象，不是各自单独对应一种独立的碎片类型。**

### 6.3 MEMORY 命令家族

**`MEMORY USAGE key [SAMPLES count]`**
- 只统计**指定的这一个key**，不会遍历全库，不会造成STW。
- 对普通字符串是精确统计；对集合类型（Hash/Set/List/ZSet），默认只抽样5个元素估算平均大小再乘总数（`SAMPLES 0`才是精确统计所有元素，元素多时会明显更慢）。
- 若要"扫描全库找大key"，应配合 `SCAN`（增量式游标，不阻塞）逐个调用，而非用 `KEYS *`。官方也提供了封装好的 `redis-cli --bigkeys` 和 `--memkeys` 工具。

**`MEMORY STATS`——实战常用字段（按关注优先级分层）**

*日常巡检看这一个*：
- `dataset.percentage`：数据本身占总分配内存的比例，低于50%就该深挖overhead去哪了

*怀疑内存异常时看这几个*：
- `allocator.allocated` / `.active` / `.resident`：三层碎片模型的核心数据源（与`INFO memory`里的同名字段是同一份数据，`MEMORY STATS`只是格式更适合程序化解析，并额外提供更细粒度的业务层拆解）
- `keys.bytes-per-key`：定义为 `dataset.bytes / keys.count`，平均每个key的数据大小，用于判断是否有异常大key拉高均值
- `peak.percentage`：当前`total.allocated`占历史峰值`peak.allocated`的比例，用于判断当前高内存是否为历史遗留

*排查特定异常时看*：
- `clients.normal` / `clients.slaves`：连接数暴涨嫌疑（含所有连接的buffer/socket开销）
- `replication.backlog`：复制积压嫌疑
- `aof.buffer`：AOF重写期间缓冲区膨胀嫌疑
- `lua.caches`：脚本缓存膨胀嫌疑（大量动态生成不同脚本文本会导致持续膨胀）

**`MEMORY DOCTOR`**：给出人类可读的通用诊断建议，适合快速初筛，不能替代`MEMORY STATS`的精确定位。

**`MEMORY PURGE`**
- 底层调用jemalloc的`arena.<N>.purge`（或`arenas.purge`）接口，强制把内部已标记为空闲、但尚未归还给OS的内存页立即归还。
- **不会移动或修改任何活跃数据**，只作用于完全空闲的内存块，因此不会影响数据完整性。
- **对"活跃页利用率差"（内部碎片高）的场景无效**——因为这类问题是"活跃数据稀疏地散落在很多页里"，这些页里还有活着的数据，不属于"完全空闲"，PURGE找不到东西可释放。必须先用active defrag搬家腾出完全空页，之后才可能被释放。
- 是在主线程**同步执行**，会阻塞其他命令，耗时取决于当前积压的闲置页数量，无法预先精确得知，生产环境应先在低峰期试跑，用`--latency`前后对比评估影响。

### 6.4 主动碎片整理（Active Defrag）

- Redis 4.0引入，默认关闭。原理：每秒计算一次碎片率，若过高则触发一轮整理——把内部数据结构重新复制到新的、更紧凑连续的内存位置，释放旧的碎片化内存。这一步依赖jemalloc提供的专门接口（绕过线程本地缓存分配，提高新分配内存彼此连续的概率）。
- **不是一次性STW式全量搬家**，而是持续的、小批量渐进式操作：处理完一小批立刻把控制权还给主线程处理正常请求，下一秒再检查一次碎片率决定是否继续。

```bash
CONFIG SET activedefrag yes
CONFIG SET active-defrag-ignore-bytes 100mb     # 碎片绝对字节数低于此值不触发，避免小实例瞎折腾
CONFIG SET active-defrag-threshold-lower 10     # 碎片率超过10%才开始整理
CONFIG SET active-defrag-threshold-upper 100    # 碎片率上限，整理强度随碎片率线性增强
CONFIG SET active-defrag-cycle-min 1            # 最低强度下占用主线程CPU的比例
CONFIG SET active-defrag-cycle-max 25           # 最高强度下占用主线程CPU的比例（节流关键参数，避免变成STW）
CONFIG SET active-defrag-max-scan-fields 1000   # 大集合类型key单次整理最多处理的元素数
```

### 6.5 排查工具选型逻辑

| 现象（数值特征） | 问题定位 | 应对手段 |
|---|---|---|
| `active/allocated` 接近1（如1.06），`resident/active` 很高（如2.74） | 囤积未归还 | `MEMORY PURGE` |
| `active/allocated` 本身很高 | 内部碎片/活跃数据稀疏 | `activedefrag`（先搬家腾出完全空页） |
| 两者都高 | 两种问题叠加 | 先defrag整理，再purge收尾 |
| `fragmentation.bytes`（绝对字节数） | 判断"值不值得处理" | 同样碎片率下，绝对浪费字节数越大，处理优先级越高 |

`fragmentation.bytes`直接给出碎片浪费的绝对字节数——同样是碎片率2.0，10MB数据集浪费10MB可能不值得处理，100GB数据集哪怕碎片率只有1.3、浪费的绝对量也可能高达30GB，判断是否需要处理应参考这个绝对值而非只看比例。

### 6.6 evicted_keys 及配套排查指标

- `INFO stats`里的`evicted_keys`：因为触发maxmemory而被主动淘汰删除的key累计数，**从进程启动开始只增不减**，除非重启或`CONFIG RESETSTAT`。
- 与`expired_keys`的区分：`expired_keys`是key自己TTL到期的自然死亡（哪怕内存充足也会被清）；`evicted_keys`是key本来还没到期（或没设TTL），但因内存不足被提前处决腾地方。
- **正确用法是采样两次算差值**（速率），单看累计值无意义：
```bash
a=$(redis-cli INFO stats | grep evicted_keys | cut -d: -f2 | tr -d '\r')
sleep 1
b=$(redis-cli INFO stats | grep evicted_keys | cut -d: -f2 | tr -d '\r')
echo "每秒淘汰速率: $((b - a)) keys/sec"
```
- **排查链路**：命中率(`keyspace_hits/(hits+misses)`)偏低 → 查`evicted_keys`增速 → 若增速高，先看`dataset.percentage`：若这个值本身很低（如30%），说明淘汰压力根源可能不是业务数据撑爆内存，而是`overhead.total`里某一项（连接数、复制积压等）偷偷占用了`maxmemory`预算，此时该排查连接/复制状态而非简单调大maxmemory或换淘汰策略。

## 扩展内容：Latency 监控体系

### 7.1 --latency 系列客户端工具的真正价值

**核心认知**：单独看一次`--latency`的读数没有意义，它的价值全部体现在"操作前 vs 操作后"或"服务器侧 vs 客户端侧"的**对比**场景中，不是用来"当场干预"，而是用来**验证因果关系、建立可比较基线、消除事后归因的不确定性**。

三种典型用途：
1. **证明因果**：一边持续监控，一边手动触发怀疑的操作（如`MEMORY PURGE`），若延迟跳高与触发时刻精确对应，即为实锤证据。
2. **排除法定位**：服务器本机测得的PING往返延迟若健康，但业务方感知延迟很高，可排除是Redis执行层问题，转向排查网络/客户端。
3. **验证优化有无副作用**：例如开启`activedefrag`前后各测一段基线，对比avg是否显著上升，判断这个优化是否"拿延迟换空间"。

**对于像`MEMORY PURGE`这类一次性同步阻塞命令**：由于是单次执行完毕、无法中途介入，"操作期间盯着看"和"操作后看"本质没区别，重点不在"何时看"，而在"测过一次、拿到具体数字"——这个数字能沉淀为运维决策依据（比如"本实例执行PURGE约耗时X毫秒，建议只在低峰期执行"）,并在事后被问及延迟异常时提供确凿归因，而非含糊猜测。

```bash
redis-cli --latency -i 1              # 持续滚动累计min/max/avg
redis-cli --latency-history -i 5      # 每N秒重新统计一段，能看出趋势变化
redis-cli --latency-dist              # 彩色分布图，区分"整体偏高"还是"偶发极端尖峰"
```

### 7.2 LATENCY 监控子系统架构

四个组成部分：
1. **埋点（hooks）**：源码中几十处关键代码路径手动埋点计时
2. **时间序列记录**：每个事件（event）独立维护一条时间序列
3. **报告引擎**：获取原始数据
4. **分析引擎**：生成人类可读报告和建议

**关键event列表**（对应贯穿本模块讲过的机制）：

| Event | 对应机制 |
|---|---|
| `command` / `fast-command` | 普通命令 / O(1)-O(logN)复杂度命令（fast-command异常触发通常说明主线程被别的事整体卡住,是"背景阻塞探测器"） |
| `fork` | RDB/AOF重写的fork()系统调用 |
| `expire-cycle` | 对应知识点4的主动过期扫描 |
| `eviction-cycle` / `eviction-del` | 对应知识点5的淘汰扫描/淘汰删除 |
| `active-defrag-cycle` | 对应知识点6的主动碎片整理 |
| `aof-write` / `aof-fsync-always` 等 | AOF相关的各具体写入/同步动作 |

**采样与存储机制**：
- `CONFIG SET latency-monitor-threshold 100`（毫秒），只有超过阈值的执行才被记为一次尖峰。默认0（关闭），因为开启开销近乎为零但没必要为健康实例平白抬高基线。
- 同一秒内同一event多次尖峰只保留最大值。
- 每个event用固定160条的环形缓冲区存历史，超过后新数据覆盖最旧数据。
- "历史最大值"单独持久记录，不受环形缓冲区覆盖影响。

**命令族**：
```bash
LATENCY LATEST                    # 所有event最近一次尖峰快照
LATENCY HISTORY event-name        # 某个event的完整历史序列（最多160条）
LATENCY GRAPH event-name          # ASCII图可视化趋势
LATENCY DOCTOR                    # 人类可读综合诊断报告
LATENCY RESET [event ...]         # 清空历史记录
LATENCY HISTOGRAM [command ...]   # 7.0+，命令级延迟的累积分布直方图（P50/P99等分位数）
```

### 7.3 LATENCY 与 SLOWLOG 的本质区别（互补而非替代）

**SLOWLOG 的边界**：只记录"客户端发来的命令"执行耗时，不包含与客户端通信、发送回复等I/O时间，也**完全不记录任何Redis内部自己触发的后台维护动作**。

**LATENCY 覆盖的范围明显更广**：可监控任意后台event，如`fork`、`aof-write`、`expire-cycle`、`eviction-cycle`、`active-defrag-cycle`——这些都是后台自动触发、客户端没有发送对应命令的维护性动作，SLOWLOG对此完全"失明"。

**典型场景**：若延迟抖动根源是主动碎片整理周期偶尔耗时较长，查SLOWLOG只会看到一堆正常的GET/SET，毫无线索；查`LATENCY HISTORY active-defrag-cycle`则能直接看到该内部事件的耗时历史，精确对应问题。

**结论**：两者覆盖范围互补——SLOWLOG负责"客户端命令层面"的慢，LATENCY负责"包括后台内部维护任务"的慢。只看SLOWLOG会对非命令类延迟问题完全失明。

### 7.4 完整实战排查流程（融合所有工具）

```bash
# 1. 确认延迟监控已开启（生产建议常年开着，阈值设低一点）
redis-cli CONFIG SET latency-monitor-threshold 20

# 2. 快速扫一眼所有event最近情况
redis-cli LATENCY LATEST

# 3. 对怀疑的具体event深挖历史趋势
redis-cli LATENCY HISTORY eviction-cycle
redis-cli LATENCY GRAPH eviction-cycle

# 4. 结合慢日志，定位具体是哪条命令、哪个客户端
redis-cli SLOWLOG GET 20

# 5. 交叉验证内存/碎片状态
redis-cli MEMORY STATS

# 6. 拿到综合建议作为最后一道保险
redis-cli LATENCY DOCTOR
```
