# 知识点1：多数据库机制

**核心结论**：Redis单实例默认支持**16个数据库**（DB 0~15，可通过`databases`配置项修改数量）。本质是**同一进程内的多个逻辑隔离的哈希表**：

```
Redis实例（同一进程）
 └─ redisDb数组
     ├─ redisDb[0] { dict: {key→redisObject, ...}, expires: {...} }
     ├─ redisDb[1] { dict: {...}, expires: {...} }
     └─ ... redisDb[15]
```

每个`redisDb`结构内部有**独立的`dict`（键值字典）和独立的过期字典**，但所有DB**共享同一个进程、同一份内存空间、同一套持久化文件（RDB/AOF）、同一套主从复制流程**——所以叫"逻辑隔离"而非"物理隔离"。

**`SWAPDB`命令**：`SWAPDB 0 1` 可以**原子性互换**两个数据库的全部数据，常用场景：在DB1预热好新数据，业务还在读DB0，预热完成后一条命令瞬间切换，客户端无感知，避免停机迁移。

**⚠️ 讨论中纠正的误区**：
- 曾把"多实例部署"和"Redis Cluster"混淆。正确区分三个概念：
  - **多数据库**（DB0~15）→ 解决同进程内的"逻辑分类"（如测试库/正式库）
  - **多实例部署**（多个独立Redis进程）→ 解决"故障隔离/资源隔离"（一个挂了不影响另一个，因为进程、内存、持久化文件都完全独立）
  - **Redis Cluster分片** → 解决"单机内存/性能瓶颈的水平扩展"（后面模块四细讲）
- **关键限制**：Redis Cluster模式下**只能使用DB0**，多数据库功能被禁用。所以想解决"用户Session和商品缓存互相隔离"的问题，正确方案是**部署两个独立实例**，而不是"进集群"（进集群反而失去了多DB能力）。

# 知识点2：RedisObject 对象模型

**核心结构**（每个key对应的value，都被包装成这个结构，而不是直接存原始数据）：

```c
typedef struct redisObject {
    unsigned type:4;      // 数据类型：string/list/hash/set/zset...
    unsigned encoding:4;  // 底层编码方式：int/embstr/raw/listpack/skiplist...
    unsigned lru:24;      // 记录最后访问时间或访问频率（供内存淘汰策略用）
    int refcount;         // 引用计数
    void *ptr;            // 指向真正的底层数据结构（int编码时直接存数值本身）
} robj;
```

**三个字段的作用**：
1. **`type`**：让Redis知道这是什么类型，操作类型不匹配时报WRONGTYPE错误（比如对String用HGET）
2. **`encoding`**：同一种类型可以有多种底层实现（如String可以是int/embstr/raw），这是理解知识点3编码转换的基础
3. **`refcount`**：配合**共享对象池**——Redis预先创建了**0~9999这10000个整数**的共享对象，多个key存相同的小整数时会共享同一个redisObject，refcount+1，不重复分配内存

**共享对象池的两个必要条件**（缺一不可）：
1. 值必须落在**0~9999范围内的整数**
2. 当前 `maxmemory-policy` **不能是** LRU/LFU相关策略

**为什么LRU/LFU策略下不能共享**：`lru`字段被LRU和LFU复用（LRU模式下记录最后访问时间，LFU模式下记录访问频率）。如果多个key共享同一个redisObject，就等于共享同一个`lru`字段——频繁访问其中一个key会让Redis误以为其他共享该对象的key也刚被访问过，导致淘汰算法判断失真（该淘汰的没淘汰，不该淘汰的被淘汰）。所以Redis设计为：**一旦配置LRU/LFU类淘汰策略，自动禁用整数共享**。

**共享对象是不可变的**：执行`INCR`等修改操作时，不会修改共享对象本身的值，而是**创建一个新的、独立的redisObject**（refcount=1）让该key指向新对象，原共享对象refcount-1，其他共享该值的key不受影响。

**GET命令的完整查找链路**：
```
key → 查DB的dict字典（哈希查找）→ 定位到redisObject
    → 检查type字段（确认是STRING）
    → 检查encoding字段：
         - 若是int：ptr本身就是数值，直接返回
         - 若是embstr/raw：ptr指向SDS结构，从SDS的buf中读取真实字符串内容返回
```

**串联知识点1**：完整存储链路是 `Redis实例 → 某个DB的redisDb → dict → key(哈希key) → value(redisObject) → ptr指向的底层数据结构`。不同DB的dict是完全独立的两张表，同名key互不干扰。

# 知识点3：五种数据类型的底层编码及字节级结构

## 3.1 String

| 编码 | 触发条件 |
|---|---|
| `int` | 值是整数，能用long表示 |
| `embstr` | 字符串长度 ≤ 44字节 |
| `raw` | 字符串长度 > 44字节 |

**验证命令**：`OBJECT ENCODING key`

### `int` 编码完整结构
```
SET age 25
```
```c
redisObject {
    type=0(STRING), encoding=7(INT), lru=..., refcount=1,
    ptr = 25   ← 直接把整数值塞进指针大小的空间，不是地址！
}
```
整体固定**16字节**，无额外内存分配，支持`INCR`直接数值运算。

### `embstr` 编码完整结构（一次性连续分配）
```
SET name "redis"
```
```
地址0x1000                                地址0x1010     0x1013
┌─────────────────────────────┬────┬─────┬────┬──────────────────┐
│ redisObject(16字节)           │len │alloc│flags│ "redis\0"(6字节)  │
│ type=0,encoding=8(EMBSTR),    │=5  │=5   │=1   │                  │
│ lru=...,refcount=1,           │    │     │     │                  │
│ ptr=0x1010 ───────────────────┼────┴─────┴────┴──────────────────┘
└─────────────────────────────┘
（sdshdr8结构：len=当前长度，alloc=分配容量，embstr下alloc==len不预留空间）
总占用：16(redisObject) + 3(sdshdr8头) + 6(buf) = 25字节，一次malloc完成
```

### `raw` 编码完整结构（两块独立内存）
```
SET bio "超长字符串...(假设90字节)"
```
```
地址0x2000（redisObject，单独一块）    地址0x3000（SDS，另一块独立内存）
┌──────────────────────┐  ptr指向  ┌────┬──────┬─────┬─────────────┐
│ type=0,encoding=9(RAW) │ ────────→│len │alloc │flags│ 90字节实际内容 │
│ lru=...,refcount=1     │          │=90 │=90   │=2   │  +结尾'\0'    │
│ ptr=0x3000             │          │(sdshdr16，用16位长度字段)      │
└──────────────────────┘           └────┴──────┴─────┴─────────────┘
两次独立malloc，总占用：16 + 5(sdshdr16头) + 90 + 1 = 112字节
```

## 3.2 Hash

| 编码 | 触发条件 |
|---|---|
| `listpack` | 字段数 ≤ 128（`hash-max-listpack-entries`） 且 每字段/值长度 ≤ 64字节（`hash-max-listpack-value`） |
| `hashtable` | 超过上述任一阈值 |

### `listpack` 编码完整结构
```
HSET user:1 name "Tom" age "25"
```
```
listpack整体格式：[totalbytes][numele][entry1][entry2]...[0xFF]

totalbytes = 45（整个listpack总字节数）
numele = 4（4个entry：name, Tom, age, 25）

Entry1: [encoding=字符串长度4][data="name"][backlen=6]
Entry2: [encoding=字符串长度3][data="Tom"][backlen=5]
Entry3: [encoding=字符串长度3][data="age"][backlen=5]
Entry4: [encoding=整数][data=25][backlen=2]  ← 纯数字会被识别为整数编码，更省空间
结尾: 0xFF（1字节终止标记）
```
**backlen的作用**：记录当前entry长度，支持**从后往前反向遍历**，这是listpack对老版本ziplist的重要改进（避免级联更新性能问题）。

### `hashtable` 编码完整结构（假设129个字段触发转换）
```c
dict {
    dictType *type;
    dictEntry **ht_table[2];   // 两个哈希表，用于渐进式rehash
    unsigned long ht_used[2];  // 值=[129, 0]
    long rehashidx;            // 值=-1，表示当前没在rehash
}
dictEntry {
    void *key;              // 指向字段名，如"f1"
    void *val;              // 指向字段值，如"v1"
    struct dictEntry *next; // 哈希冲突时指向下一个entry（链式处理）
}
```
```
ht_table[0]（假设桶数量256）：
bucket[1] → dictEntry{key="f88", val="v88", next=NULL}
bucket[2] → dictEntry{key="f1", val="v1", next=→{key="f45",val="v45",next=NULL}}  ← 哈希冲突链式存储
...
ht_used[0] = 129
```
每个dictEntry约**24字节**（key指针8+val指针8+next指针8），129个entry约占3096字节，远超listpack的45字节级别——这就是hashtable"费内存但O(1)查找"的原因。

## 3.3 List

| 编码 | 触发条件 |
|---|---|
| `listpack` | 元素少且短（Redis 7.0+新特性，小列表直接用一个listpack） |
| `quicklist` | 超过阈值（`list-max-listpack-size`） |

### `listpack` 编码
```
RPUSH mylist a b c
```
格式同Hash的listpack：`[totalbytes=15][numele=3][Entry'a'][Entry'b'][Entry'c'][0xFF]`

### `quicklist` 编码完整结构（假设1000个元素）
```c
quicklist {
    quicklistNode *head;   // 指向第一个节点
    quicklistNode *tail;   // 指向最后一个节点
    unsigned long count;   // 值=1000（总元素数）
    unsigned long len;     // 值=8（节点/listpack块数，1000/128≈8）
}
quicklistNode {
    struct quicklistNode *prev;
    struct quicklistNode *next;
    unsigned char *zl;         // 指向本节点内部listpack起始地址
    unsigned int sz;           // 值=520（本节点listpack总字节数）
    unsigned int count:16;     // 值=128（本节点含128个元素）
    unsigned int encoding:2;   // 值=2（表示内部可能用LZF压缩过）
}
```
```
quicklist{count=1000, len=8}
Node1{count=128,sz=520} ←prev/next→ Node2{count=128,sz=515} ←...→ Node8{count=104,sz=430}
   │zl                                  │zl
   ↓                                    ↓
[item1..item128]的listpack           [item129..256]的listpack
```
本质是**"链表的链表"**：外层双向链表实现两端O(1)插入删除，每个节点内部又是紧凑的listpack，兼顾大数据量效率和存储紧凑性。

## 3.4 Set

| 编码 | 触发条件 |
|---|---|
| `intset` | 所有元素都是整数，且数量 ≤ 512（`set-max-intset-entries`） |
| `listpack` | 存在非整数元素，但数量少、长度短 |
| `hashtable` | 超过阈值 |

### `intset` 编码完整结构
```
SADD nums 5 3 8 1
```
```c
intset {
    uint32_t encoding;  // 值=2（INTSET_ENC_INT16，因为元素都能用int16表示）
    uint32_t length;    // 值=4
    int16_t contents[]; // 值=[1, 3, 5, 8] ← 自动排序后的数组！
}
```
```
┌──────────┬─────────┬──────┬──────┬──────┬──────┐
│encoding=2 │length=4 │  1   │  3   │  5   │  8   │
└──────────┴─────────┴──────┴──────┴──────┴──────┘
每元素占2字节，总占用4+4+4×2=16字节
```
插入超过int16范围的数（如70000）会**整体升级**为int32数组，所有旧元素重新拷贝一遍。

### `listpack` 编码（Set）
```
SADD names "Tom" "Jerry"
```
格式同Hash listpack：`[Tom][Jerry]`连续存放。

### `hashtable` 编码（Set）
```c
dictEntry { key="233", val=NULL, next=... }  // val恒为NULL，Set只关心元素是否存在
```

## 3.5 ZSet

| 编码 | 触发条件 |
|---|---|
| `listpack` | 元素数量 ≤ 128 且 每元素长度 ≤ 64字节 |
| `skiplist` | 超过阈值 |

### `listpack` 编码完整结构
```
ZADD scores 90 "Tom" 85 "Jerry"
```
```
totalbytes = 20
numele = 4  ← member和score分开算，各占一个entry
Entry1: [字符串]"Tom"    Entry2: [整数]90
Entry3: [字符串]"Jerry"  Entry4: [整数]85
0xFF
```
member和score**顺序相邻存放**，查找需顺序扫描比对member字符串。

### `skiplist` 编码 —— 完整深入展开

**要解决的问题**：避免ZSet做`ZRANGEBYSCORE`等范围查询时，在数据量大的情况下进行O(N)顺序扫描。

**核心思想**：在有序链表基础上叠加多层"跳跃通道"，层数越高跨度越大（类比高速公路出口越少跑得越快），**用空间换时间**。

```c
struct zset {
    dict *dict;    // 负责O(1)按member查score
    zskiplist *zsl; // 负责O(logN)按score排序遍历
}
struct zskiplistNode {
    sds ele;                          // member，如"user_88"
    double score;                     // 分数
    struct zskiplistNode *backward;   // 反向指针，支持ZREVRANGE
    struct zskiplistLevel {
        struct zskiplistNode *forward; // 本层指向的下一节点
        unsigned long span;            // 跨度，用于快速累加计算排名
    } level[];   // 每个节点插入时随机生成层数，层数越高概率越低（最大32层）
}
```

**完整8节点数值化示例**（A~H, score分别10,20,...80）：

假设随机分配后各节点高度：A=1, B=2, C=1, D=3, E=1, F=2, G=1, H=2（D是全局最高节点，高度3）

```
Level3:  HEAD ────────────────────────────→ D(span=4) ──────────────────→ NULL
Level2:  HEAD ──────→ B(span=2) ──────→ D(span=2) ──────→ F(span=2) ──────→ H(span=2) → NULL
Level1:  HEAD→A→B→C→D→E→F→G→H→NULL（每步span=1）
```

节点D的完整字段（高度3的节点）：
```c
zskiplistNode {
    ele="D", score=40.0,
    backward=C,
    level[0]: {forward=E, span=1}
    level[1]: {forward=F, span=2}   // 跨过E，到F
    level[2]: {forward=NULL, span=0} // Level3没有更高节点了
}
```

**查`ZRANK G`的完整跳转推演**：
1. Level3：HEAD.level[2].forward=D，D.score(40)≤目标(70)→可跳，rank累加span=4→**rank=4**；D在Level3无下一节点，降层
2. Level2：D.level[1].forward=F，F.score(60)≤70→可跳，rank+=2→**rank=6**；F.level[1].forward=H，H.score(80)>70→不可跳，降层
3. Level1：F.level[0].forward=G，G.score(70)≤70(相等也算)→可跳，rank+=1→**rank=7**；到达目标G，停止
4. 最终排名（从0开始计数）= rank-1 = **6**

**验证**：A,B,C,D,E,F,G共7个节点排在G（含自身）之前或等于G，索引第6个（从0数），结果一致。

**效率对比**：普通链表需要7步顺序遍历才能找到G，跳表只需**3次跳跃**（HEAD→D→F→G）加几次降层判断，数据量越大加速效果越明显（约log₂N级别）。

**为什么要dict+skiplist双结构**：

| 操作 | 用哪个结构 | 复杂度 | 原因 |
|---|---|---|---|
| `ZSCORE`（按member查分数） | dict | O(1) | 哈希查找，恒定不变 |
| `ZRANK`（查排名） | skiplist | O(logN) | 依赖有序性，逐层跳跃 |
| `ZRANGEBYSCORE`（按分数范围查） | skiplist | O(logN) | 同上 |
| `ZADD`（插入，两边都要同步） | dict+skiplist | O(logN) | 两个结构都要维护 |

## 通用规则总结

1. **编码转换只会由简单→复杂，不会自动变回去**（即使删除数据变少），除非`DEBUG RELOAD`或重启重新从RDB加载
2. 所有"listpack系列"编码都是Redis 7.0+对老版本`ziplist`的替代（修复了级联更新性能问题）
3. 所有阈值均可在`redis.conf`调整（如`hash-max-listpack-entries`），本质是**内存 vs 性能**的权衡：调大阈值→更多数据用紧凑结构（省内存但操作变慢）；调小阈值→更早转换为标准结构（费内存但操作快）
