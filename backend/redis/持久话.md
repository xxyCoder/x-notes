## 知识点7：RDB 快照原理

### 7.1 本质
RDB 是某一时刻整个数据集的二进制快照文件，恢复时是"整体替换"（反序列化直接重建内存结构），不是命令重放。

### 7.2 三种触发方式

| 方式 | 是否阻塞 | 说明 |
|---|---|---|
| `SAVE` | 阻塞整个Redis | 主线程直接执行，写完前不响应任何请求 |
| `BGSAVE` | 仅fork瞬间阻塞 | fork子进程异步写文件，生产环境标准方式 |
| `save <seconds> <changes>` | 同BGSAVE | 多条规则为"或"关系，任一满足即自动触发BGSAVE |

**日志识别触发来源**（看`Background saving started`前一行）：
- 自动规则触发：前面有"X changes in Y seconds. Saving..."
- 从库全量同步触发：前面有"Starting BGSAVE for SYNC with target: disk"（或diskless模式对应提示）
- 手动触发：无任何前置提示行

### 7.3 fork() 与 COW 机制

**fork()复制内容**：只复制页表，不复制物理内存页。父子进程共享同一份物理内存，子进程看到的是fork那一瞬间的完整快照。

**fork耗时决定因素**：取决于页表大小，页表大小取决于内存占用量。例：24GB实例，页表大小约为24GB÷4KB×8字节≈48MB，fork时需分配复制这份页表。

**fork耗时与虚拟化平台强相关**：同样数据规模，不同虚拟化平台每GB耗时可差一到两个数量级，某些跑在Xen上的实例性能损耗可达其他环境的十到百倍。云上部署应优先确认底层虚拟化类型（避免老旧Xen，优先HVM/KVM）。

**COW真正的触发机制**：
- fork之后主进程**只读**数据 → 不触发COW，父子进程共享物理页
- 主进程**写**数据 → 触发COW，操作系统复制这一页（通常4KB），主进程改副本，子进程持有旧页
- **关键细节**：Linux为了让fork()更快，连页表项本身的复制也是懒惰的，推迟到真正发生页错误时才做。这意味着COW的开销不集中在fork()调用本身，而是摊在了整个持久化窗口期间、每一条恰好碰到未复制页的写命令响应延迟里，不是一个独立可见的耗时数字。真实案例中曾出现fork仅耗时6ms，但整体延迟尖刺达300ms的现象，差值即来自这种分散的页错误开销。

**Transparent Huge Pages（THP）对COW的放大效应**：
- THP默认把多个4KB页合并成2MB大页管理，用于减少页表项数量、降低TLB压力
- 开启THP后，一次页错误的处理单位从4KB变成2MB，即使只改1字节也要整页复制，代价放大约500倍
- 这会让COW字节数本身（不只是耗时）明显更大，因为复制的最小单位变大了
- 实测对比：同样负载下，用jemalloc分配器时最大延迟尖刺可达339ms，换成普通malloc则降到21ms，分配器和内存布局对COW代价有显著影响
- 处理命令：`echo never > /sys/kernel/mm/transparent_hugepage/enabled`，需写入启动脚本长期生效（临时命令重启后失效）
- Redis启动时会主动检测THP状态并在日志中警告

### 7.4 RDB文件格式

```
"REDIS" + 4位版本号        → 文件头（9字节）
[SELECTDB opcode] + db编号
[EXPIRETIME_MS opcode] + 8字节毫秒时间戳   → 可选，紧跟在有TTL的key前
[类型标识] + key + value    → 按各类型专属编码序列化（直接搬运底层数据结构字节流）
...（重复）
0xFF                       → EOF标记
8字节 CRC64 校验和
```

直接序列化数据结构本身（而非记录命令），是RDB体积小、加载快的根本原因。

### 7.5 加载过程
启动时若存在RDB文件，`rdbLoad()`按格式顺序解析重建RedisObject。**该过程是阻塞的**——加载完成前Redis不对外提供服务。

### 7.6 fork/COW 监控体系

**fork耗时**：
- `latest_fork_usec`：只包裹fork()系统调用本身耗时（微秒），不含子进程写文件、不含COW。**瞬时值**，每次fork覆盖上一次，不做累积平均
- 局限：轮询周期长于fork发生频率会错过异常值；需配合`LATENCY HISTORY fork`（最近160条历史采样，前提是`latency-monitor-threshold`设置足够低才能捕捉到）和`LATENCY DOCTOR`（给出频率、离散度综合分析）弥补

**COW大小**（无直接耗时字段，只有字节数字段）：
- `current_cow_size` / `current_cow_peak` / `current_cow_size_age`：持久化进行中的实时值，进程结束归零
- `rdb_last_cow_size` / `aof_last_cow_size`：上一次对应操作的COW终值，事后仅存这一个数字，无过程曲线
- Redis 7.0+新增通用字段（不区分RDB/AOF，因任意时刻只允许一个持久化子进程存在）：还包括`current_fork_perc`（当前进度百分比）、`current_save_keys_processed`、`current_save_keys_total`

**没有直接耗时字段的原因**：COW不是一次性事件，而是分散在整个持久化窗口内的大量页错误，没有统一起止边界可以打包成一个时间数字。字节数和实际耗时代价不是线性对应关系——同样的COW字节数，THP开启/关闭下的真实延迟代价可能相差一个量级。

**间接推算COW真实延迟代价的手段**：
1. 前后对比法：`redis-cli --latency-history`挂着跑，同时触发`BGSAVE`/`BGREWRITEAOF`，对比窗口内延迟变化
2. 高频采样画曲线：每100ms抓一次`INFO persistence`记录`current_cow_size`，自行拼出增长速率曲线
3. Watchdog抓栈：Redis内置软件看门狗功能，能在延迟事件发生时打出进程调用栈，直接定位卡顿指令
4. `rdb_last_bgsave_time_sec`：只能当粗略上限参考，磁盘I/O时间和COW时间混在一起无法拆分

## 知识点8：AOF 日志原理

### 8.1 本质
记录每一条写命令本身，恢复靠重放命令重建数据集。

### 8.2 文件格式：RESP协议编码
例如`SET name redis`存储为：
```
*3
$3
SET
$4
name
$5
redis
```
选择RESP格式是为了让加载AOF时能直接复用处理客户端请求的解析逻辑。

### 8.3 写入三层路径
```
① 命令执行完 → 编码RESP → 追加进 aof_buf（纯内存，瞬时）
② beforeSleep阶段 → write() → 数据从aof_buf进内核页缓存（未真正落盘）
③ fsync() → 页缓存内容真正刷到磁盘物理介质（真正安全）
```
`write()`快（微秒级），`fsync()`慢（真实磁盘I/O）。

### 8.4 appendfsync 三种策略

| 策略 | 行为 | 丢失窗口 | 性能 |
|---|---|---|---|
| `always` | 每条命令后立刻同步fsync | 最多丢1条命令 | 最差 |
| `everysec`（默认/推荐） | 独立后台线程每秒fsync一次 | 最多丢1秒（极端情况可能扩大到接近2秒） | 接近无fsync开销 |
| `no` | 完全交给操作系统决定 | 最大最不可控 | 最好 |

**everysec隐藏坑**：若磁盘慢导致fsync超时未完成，主线程下一次write可能被迫推迟（避免与正在进行的fsync抢占同一文件），实际丢失窗口可能从1秒扩大到接近2秒。

### 8.5 为什么需要重写：AOF文件无限膨胀问题
同一key反复修改会产生大量冗余命令记录，导致文件体积持续增长、恢复重放耗时越来越长。

### 8.6 重写核心思路
**不是压缩旧文件，而是完全抛开旧文件，直接遍历当前内存数据集，为每个key生成能重建当前状态的最少命令**，写入全新文件。

### 8.7 触发方式

**手动**：`BGREWRITEAOF`

**自动**：由两个配置项共同控制
```
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```
判断公式：
```
增长率 = (aof_current_size - aof_base_size) / aof_base_size
```
增长率≥设定百分比，**且**`aof_current_size`超过`min-size`，两条件同时满足才触发。`min-size`用于防止小文件反复触发重写。

### 8.8 重写执行过程（Redis 7.0+ 多部分AOF机制）

1. 主进程fork出子进程
2. 子进程拿fork那一刻的内存快照，遍历所有key，生成最小化命令集合，写入新的基础文件（期间伴随COW，COW不是独立步骤，是遍历过程中伴随发生的背景现象）
3. **父进程同时**打开独立的新增量文件，把重写期间的新写入命令继续走正常的日常写入管线（aof_buf→write()→按everysec节奏fsync()），写进这个增量文件
4. 子进程完成后，父进程更新manifest清单文件，记录当前有效的base文件和incr文件是哪些
5. 无需传统意义的"合并"和"rename替换"

### 8.9 排队机制：RDB与AOF重写子进程不会同时存在

Redis规定任意时刻只允许一个持久化相关子进程运行。若BGREWRITEAOF触发时恰好有BGSAVE在进行，会标记为排队等待：
- `aof_rewrite_scheduled` / `aof_pending_rewrite`：官方定义文字相同，均表示"重写将在当前RDB快照结束后被调度执行"

**设计原因（两层，不是笼统的"性能"）**：
1. 避免两个子进程同时fork，争抢磁盘I/O和CPU资源
2. 避免COW开销叠加：若两个子进程在不同时刻各自持有不同世代的内存快照，主进程每次写操作可能要同时为两个世代的物理页做复制，COW代价翻倍。排队串行避免这种不必要的叠加

### 8.10 6.x方案 vs 7.0+方案差异

**6.x方案（内存缓冲区aof_rewrite_buf）**：重写期间新写入命令额外复制一份堆积进内存中的`aof_rewrite_buf`（与aof_buf并存，主线程需双写）。子进程完成后，父进程把这个缓冲区**一次性追加写入**新文件，再rename替换旧文件。

真正痛点：不是"要不要写磁盘"，而是这次一次性大批量写入本身会造成**集中的延迟尖刺**（重写耗时长、期间QPS高时缓冲区可能膨胀到几十上百MB），同时该缓冲区无上限保护，存在内存占用失控风险。

**7.0+方案（独立增量文件）**：重写期间新写入直接走正常写入管线写入独立磁盘增量文件，磁盘I/O总量不变，但被摊平在整个重写窗口期间，不存在憋到最后一次性爆发写的动作。收尾只需更新manifest（极小的元数据操作）。

**本质**：省掉的不是磁盘写入耗时本身，而是消除了"耗时集中在一个点爆发"的糟糕时间分布，顺带消除内存缓冲区无限膨胀风险。

### 8.11 重写期间的双写代价（6.x场景明显）
主进程需同时维护`aof_buf`（常驻，与是否重写无关）和`aof_rewrite_buf`（仅重写期间存在，结束即清空）两份独立结构。

### 8.12 INFO persistence 全部AOF相关字段

**体积类**
| 字段 | 含义 |
|---|---|
| `aof_current_size` | 当前AOF文件总大小（字节） |
| `aof_base_size` | 上次重写完成后的基准文件大小（字节），是增长率计算的分母 |

**重写状态标志类**
| 字段 | 含义 |
|---|---|
| `aof_rewrite_in_progress` | 是否有重写正在执行中 |
| `aof_rewrite_scheduled` | 重写是否排队等待RDB快照结束后调度 |
| `aof_pending_rewrite` | 官方定义与上一字段文字相同 |

**上次重写结果类**
| 字段 | 含义 |
|---|---|
| `aof_last_rewrite_time_sec` | 上次重写耗时（秒）。**计时起点**是fork()发起（等同BGREWRITEAOF触发）；**计时终点**是整个重写操作彻底完成（子进程写完文件+父进程完成manifest更新等全部收尾）。fork本身只占极小部分，绝大部分时间是子进程实际扫描内存、写磁盘所花时间 |
| `aof_current_rewrite_time_sec` | 当前重写已耗时；**-1为约定值，代表当前没有重写在跑**，不是字面负数秒 |
| `aof_last_bgrewrite_status` | 上次重写是否成功（ok/err） |
| `aof_rewrites` | 累计成功重写次数（只增不减） |
| `aof_rewrites_consecutive_failures` | **连续**失败次数，一次成功即清零 |

**写入与同步链路类**（everysec模式核心诊断字段，完整因果链条）：
```
根源：磁盘慢，后台fsync迟迟做不完
        ↓
aof_pending_bio_fsync 堆积（已提交给BIO后台线程、排队等待执行的fsync任务数）
        ↓
主线程准备write时发现文件正被fsync占用，被迫放弃这次write
        ↓
aof_delayed_fsync +1（记录"write被推迟发生"的累计次数，是"动作次数"）
        ↓
数据出不去，只能继续留在内存里
        ↓
aof_buffer_length 随之升高（记录aof_buf中未写出的字节数，是"体积"）
```
三者是链路上不同环节的信号，`aof_pending_bio_fsync`堆积是根源信号→`aof_delayed_fsync`增长是被打断动作本身的计数→`aof_buffer_length`升高是这个打断导致的堆积后果。三者任一持续偏离0，都指向磁盘fsync能力跟不上写入节奏。

**整体状态类**
| 字段 | 含义 |
|---|---|
| `aof_enabled` | AOF是否开启，为0时上述所有运行时字段均不显示 |
| `aof_last_write_status` | 上一次**单条写命令**追加到AOF是否成功（与`aof_last_bgrewrite_status`是完全不同的两件事，前者是日常高频单命令写入健康度，后者是整体重写操作成败） |
| `aof_last_cow_size` | 上一次AOF重写产生的COW总字节数（终值） |

### 8.13 IOPS 与 fsync 的关系（补充机制）

fsync()要落地依赖发起真实I/O操作，会占用存储设备的IOPS配额。一次fsync可能因文件系统日志（journal）和设备缓存刷新（cache flush）而拆解成多次物理I/O，实际消耗的IOPS可能不止1。当实际所需I/O请求量超过设备IOPS上限，多余请求进入排队，且利用率越接近饱和，排队延迟增长越剧烈（非线性）。云盘还存在"基线IOPS+突发信用池"机制，信用耗尽后IOPS骤降，会导致间歇性、无规律的性能抖动——这正是`aof_pending_bio_fsync`堆积、进而`aof_delayed_fsync`增长的物理根源。

### 8.14 AOF文件损坏的两种情形与处理方式

**尾部截断（正常可预期现象）**：断电等系统崩溃场景下，AOF文件末尾可能出现半截命令。原因不是Redis应用层的fsync策略问题，而是文件系统层面（如ext4的`data=ordered`/`writeback`模式）对"元数据"和"数据内容"落盘顺序的一致性保证问题——文件元数据可能已显示文件变长，但实际内容还未落盘。这种情况**任何`appendfsync`策略下都可能发生**，不是`everysec`独有。Redis默认开启`aof-load-truncated`，加载时识别到文件末尾不完整会直接丢弃这条命令，前面已完整读到的命令正常生效，不会导致整个加载失败。

**中间损坏（异常错误）**：如磁盘坏道导致文件中间数据损坏，Redis启动时会拒绝加载并报错退出，不会自动跳过继续。需要人工使用修复工具：
```
redis-check-aof --fix appendonly.aof
```
该工具会扫描到损坏点之前的所有有效命令，截断丢弃损坏点之后的内容，生成可用文件，损坏点之后的数据必然丢失。

## 知识点9：混合持久化

### 9.1 设计动机
RDB恢复快但数据丢失窗口大，AOF数据安全但恢复慢（需逐条重放命令）。混合持久化的思路是把两种格式拼接在同一个文件里，兼得两者优点。

### 9.2 开启配置
```
aof-use-rdb-preamble yes
```
（Redis 4.0引入，7.0+默认开启）

### 9.3 文件结构
开启后，AOF重写产生的新文件由两段拼接而成：
```
[RDB格式的数据快照]  +  [AOF格式的增量命令]
```
前半段：`BGREWRITEAOF`执行时，子进程把当前内存数据按RDB二进制格式写入文件开头。
后半段：从重写开始那一刻起，新产生的写命令继续按AOF的RESP文本格式追加在后面。

### 9.4 加载过程
Redis利用RDB格式自带的结束标记（`0xFF`+8字节CRC64）来区分两段：从文件开头按RDB规则解析，读到该标记为止，这段直接反序列化重建内存对象；标记之后的剩余部分切换为AOF解析方式，逐条按RESP协议解析重放。

### 9.5 收益
**恢复速度**：占绝大部分数据量的存量部分是RDB格式，直接反序列化，速度接近纯RDB；只有重写后新增的少量增量命令需要逐条重放。
**数据安全性**：整体仍是AOF体系持续追加维护，丢失窗口与纯AOF一致（如`everysec`最多丢1秒），不会因为用了RDB前半段而退化成RDB级别的丢失窗口。

### 9.6 与AOF重写机制的关系
混合持久化不是独立的持久化开关，而是**依附在AOF重写这个动作上生效**：
- 若未开启`appendonly yes`，该配置不起作用
- 每次`BGREWRITEAOF`触发时，若`aof-use-rdb-preamble`开启，生成的基础文件用RDB格式写；关闭则退回传统纯RESP命令格式
- 7.0+的重写流程本身（独立增量文件+manifest管理）不受影响，混合持久化只改变"基础文件内部用什么格式写"

### 9.7 与Redis 7.0多部分AOF结合后的文件结构
```
appendonlydir/
  ├── appendonly.aof.1.base.rdb       ← 基础文件，开启混合持久化时为RDB格式（后缀.rdb）
  ├── appendonly.aof.1.incr.aof       ← 增量文件，纯AOF/RESP命令格式
  └── appendonly.aof.manifest         ← 清单文件，记录当前有效的base文件和incr文件
```
若关闭混合持久化，基础文件后缀变为`.base.aof`，内容为纯文本RESP命令流（重写后的最小化命令集，但仍是命令形式，非数据结构直接序列化）。

**重启加载完整顺序（结合manifest机制）**：
1. 先查manifest确认当前有效的base文件和incr文件
2. 按RDB规则解析base文件（若为.rdb格式则反序列化；若为.aof格式则逐条重放），将内存恢复到"重写完成那一刻"的状态
3. 再按RESP协议逐条解析并重放incr文件中的命令，在已有状态基础上继续叠加
4. **顺序不能颠倒**：incr文件里的命令（如某key的INCR）依赖base文件已建立的初始状态，若先重放incr会导致对不存在或状态错误的key执行命令，结果错乱

### 9.8 局限性
文件前半段（base.rdb）是二进制内容，无法用文本编辑器直接查看和人工编辑修复，需要专门工具解析。开启混合持久化后，基础文件的可读性和可编辑性下降。

### 9.9 恢复速度对比（有/无混合持久化）
关闭混合持久化时，base文件即使是重写后的最小化命令集，依然需要Redis命令处理器逐条解析执行才能重建数据结构；开启后base部分是直接反序列化重建内存对象（类似整体复制），不需要逐条执行命令。数据量越大，这个速度差距越明显。

## 知识点10：持久化对比与选型建议

### 10.1 三者全面对比

| 维度 | RDB | AOF（纯） | 混合持久化 |
|---|---|---|---|
| 数据安全性 | 差，取决于save规则，可能丢几分钟 | 好，`everysec`最多丢1秒 | 好，等同AOF |
| 恢复速度 | 快，直接反序列化 | 慢，逐条重放命令 | 快，接近RDB水平 |
| 文件体积 | 小，紧凑二进制 | 大，命令文本流水账 | 中，比纯AOF更紧凑 |
| 是否阻塞 | fork瞬间阻塞（COW开销） | 重写时同样有fork+COW开销 | 同AOF |
| 适合场景 | 备份、迁移、主从复制基准点 | 主要数据安全手段 | 生产首选 |
| 可读性 | 二进制不可编辑 | 纯文本可读 | base部分不可读，incr部分可读 |

### 10.2 同时开启RDB和AOF时，重启加载的优先级规则

**只要`appendonly yes`（AOF开启），重启时永远优先加载AOF，完全忽略RDB文件**，即使RDB文件更新时间更新也一样。这不是"比较哪个更新"，而是只要AOF开着，RDB就完全不参与重启加载流程，RDB此时的价值仅限于主从复制和手动备份。

**实际影响**：若经历过"关闭AOF→期间生成RDB→重新开启AOF"的操作序列，中间产生的RDB快照，重新开启AOF后不会被自动用于恢复，除非手动干预。

### 10.3 `save`规则与主从复制中RDB生成能力的关系（重要辨析）

`save <seconds> <changes>`配置控制的**只是"是否按固定时间/次数规则自动定时生成RDB"**，与RDB这套机制本身是否可用无关。主从复制的全量同步依赖`BGSAVE`这个**按需触发**的能力，与`save`规则是否配置**完全无关**——即使注释掉所有`save`规则，只要某个从库需要全量同步，主库依然会正常fork生成RDB。

**因此，注释掉`save`规则并不会导致"主库没有RDB可用于全量同步"**，这一点不能作为反对关闭`save`规则的理由。

### 10.4 关闭`save`规则的真实风险点

1. **失去独立的、可预测时间点生成的RDB备份文件**：定时`save`产生的RDB可按稳定节奏被外部脚本用于异地拷贝、归档备份；关闭后若想要一份干净RDB用于备份迁移，只能靠人工/脚本额外调用`BGSAVE`
2. **BGSAVE触发时机从可控变为不可控**：一旦某从库掉线重连需要全量同步，主库必须临时fork生成RDB，这个开销并未消失，只是从"可选定的业务低谷期"变成"随机时间点，可能恰好撞上业务高峰期"
3. **AOF不适合替代RDB承担备份迁移用途**：AOF是持续增长、格式相对复杂（尤其开启混合持久化后）的活跃文件，不像RDB是单一时间点的紧凑快照，两者用途本不完全重叠——AOF负责数据安全恢复，RDB负责备份与迁移

### 10.5 主从全量同步中，RDB快照与新增写入的衔接机制

主库fork子进程生成RDB快照的同时，会**额外把fork之后新收到的写命令，缓存进这个从库专属的输出缓冲区**（大小受`client-output-buffer-limit replica`参数控制）。RDB生成完毕传给从库、从库加载完成后，主库把这段时间攒下的缓冲区命令流式发送给从库，让其追上最新状态。这与AOF重写期间`aof_rewrite_buf`的设计思路一致：都是"fork那一刻的快照"+"fork之后新发生的操作单独缓存，事后补发"。

**潜在风险**：若数据量太大、传输太慢，或从库消化缓冲区速度跟不上主库写入速度，该缓冲区可能被写满。默认硬限制通常为256MB，若RDB快照体积接近或超过该值，主库会在传输过程中直接断开该从库连接，导致全量同步失败，从库需重新发起同步请求；若数据量持续过大而未调整该限制，可能陷入"同步→缓冲区写满→断开→重新同步"的循环。
