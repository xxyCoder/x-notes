## 引子：无状态 HTTP，验明正身的事实无法跨请求存活

密码验证通过了,服务器确认“你是 admin”。然后下一个请求 `GET /api/me` 来了，服务器问：你是谁？

HTTP 是**无状态**的：每个请求相互独立，服务器不记得上一个请求发生过什么，TCP 连接都不保证是同一条。登录请求里完成的“验明正身”，到下一个请求就蒸发了。这是登录需求的真正难点：**怎么让"验证通过"这个事实跨越请求活下来。**

结论：**密码只验一次，验完换发“通行证”，之后凭通行证进出。** 登录系统 = 通行证的发行、核验、换发、回收

## 方案一 Session + Cookie：登记簿模式

机制:服务端设一本登记簿（`sessions`: sessionID → 用户信息，生产放 Redis），浏览器只保管一个编号。

```go
sid := newToken()                        // 64 位随机 hex
sessions[sid] = &sessionInfo{...}        // 登记簿记账
http.SetCookie(w, &http.Cookie{
    Name: "session_id", Value: sid,
    HttpOnly: true,                      // JS 读不到 → 防 XSS 偷
    SameSite: http.SameSiteLaxMode,      // 跨站请求不自动带 → CSRF 防御地基
    MaxAge: 1800,
})
```

**sessionID 的安全性质是"猜不出",不是"解不开"。** 它是 32 字节密码学随机数，本身毫无意义，意义全在服务端登记簿里。

攻击者面对两条路：**自己伪造**——要在 2²⁵⁶ 的空间里猜中一个合法编号的概率约等于零；**偷一个真的**——有效，能用直到过期或被删，所以 HttpOnly 防 XSS 偷 cookie 才这么关键。

**Cookie 三件套**:
- `HttpOnly`：浏览器禁止 JS 读此 cookie。没有它,任意 XSS 脚本 `document.cookie` 即偷走通行证;有了它,凭证只在浏览器和服务器间自动往返
- `SameSite=Lax`：跨站请求不自动携带 → CSRF 防御的地基
- `Secure`：仅密信道(上 HTTPS 后开)
- 同站请求浏览器**自动附带** cookie → 前端零代码，Session 成为传统 Web 默认方案的原因

**状态在服务端,一好一坏**：
- 好：**删登记簿一行 = 立即下线**。可撤销性最强，封号/踢下线/改密码全端失效都是一次 delete
- 坏：**有状态**。集群里每台机器都要查得到 → 必须共享存储(Redis)；每请求多一次查询；Redis 挂了全员掉线

## 方案二 JWT:防伪证件模式

动机：为水平扩展/微服务而生——验证不查任何存储。

结构：`header.payload.signature` 三段 Base64URL 用点连接。

**要点一:前两段只是编码,不是加密。** payload 一解码就是 `{"uid":1,"sub":"admin","iat":...,"exp":...}`，任何人都能读。签名只保证"不可篡改"，不保证"不可读"→ **JWT 里永远不放手机号、权限明细等敏感信息**。

**要点二:签名在数学上做的事。** `signature = HMAC-SHA256(header.payload, secret)`。HMAC 把只有服务器知道的 secret 搅进哈希：不知道 secret 就造不出合法签名；内容改一个字节(uid 从 1 改成 2)，签名面目全非。签名 = 防伪钢印，secret = 刻章私钥，必须走环境变量——硬编码进仓库 = 推送当天全线失守(任何人可伪造任意用户)。

**要点三:验证 = 纯计算,零存储,代价是收不回。** 验签 + 查 exp 就完事，加 100 台机器不需要共享任何东西。但签出去的 token 在 exp 前 **无法收回** ——登出只能前端删 token（"假登出",被偷的副本照样能用）。这是 JWT 的死穴,方案三存在的理由。

**要点四:alg:none 血泪教训。** 早年一些库从 token header 里读“用什么算法验签”，攻击者把 alg 改成 `none` 声称"无需签名"，库信了 → 伪造通过。防御原则：**算法由验证代码写死,永不读对方声称的算法**。

## 本关核心概念:过期 ≠ 撤销

- **过期(exp)**：被动的、**时间驱动** 的死亡。死期在签发时写死在 token 里，服务器只是读表确认
- **撤销**：主动的、**事件驱动** 的死亡。签发后、自然死亡前，因事件(登出/改密码/封号/泄露)需要立即失效

两条歧路:
- "把 exp 调短" → 是 **缩小不可撤销窗口** ，不是撤销；推到底（频繁续期）就重新发明了 refreshToken
- “加黑名单“ → 每请求多查一次 Redis，状态回来了，等于更贵的 session

## 方案三 双 Token:把两种哲学在时间轴上拼接

僵局：要可撤销 → 状态在服务端；要无状态扩展 → 服务器不存东西。双 token 的洞察：**不必全局二选一,在时间轴上拆开**。

- **accessToken**：2h 短命 JWT，**无状态** 到处用 → 拿扩展性；被偷窗口只有 2h
- **refreshToken**：30d 长命 **随机串**（同 sessionID 路线），**服务端有登记** → 拿可撤销性

```
登录：发 access(2h) + refresh(30d,登记)
日常：只带 access → 验签,零存储
过期：拿 refresh 换新 → 发一对新的，旧 refresh 当场作废
登出/改密码：删服务端 refresh → 全端下线（access 最多再活 2h）
```

**为什么必须轮换**：refresh 被偷时，攻击者和真用户**抢着刷新**，后到的 401，异常立刻暴露。更严格的生产做法：检测到已作废的 refresh 再次出现 → 清空该用户全部 refresh，断定泄露，强制重登。

**残余窗口(双 token 是压缩,不是消灭)**:

| 方案 | 登出/泄露后的最坏残留 |
|---|---|
| 单 JWT 长效(7 天) | 最长 7 天收不回 |
| 双 token | 最长 = accessTTL(2h) |
| Session | 0,删表即死 |

TTL 权衡：压到 1 分钟窗口最小，但 refresh 换发太频繁(网络往返、被截获面、并发刷新复杂度)，主流 15min~2h。**业务要求"登出立即生效"(银行/内部后台)→ 直接用 Session,别给 JWT 打补丁。**

**状态粒度谱系**（想要“立即死”又想保扩展性时的中间路线）：

```
无状态(纯 JWT)      每用户一条 gen          每凭证一条(session/refresh 表)
窗口 = TTL           窗口 = 0               窗口 = 0
状态 = 0             状态 = 1 个整数/用户    状态 = 每次登录一条
```

gen 方案：JWT 里加"凭证代次"字段，改密码/全端登出时 gen+1，验证时查一眼是否匹配——任意时刻全端立即死亡，状态只有一个小整数。天下没有免费的午餐：**窗口每缩小一档,状态就多一档**。
