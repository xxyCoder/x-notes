# React 事件系统

## 一、为什么集中处理事件

先分清两件事：

- **集中监听**：React 通常在根容器等位置注册原生监听器，而不是给每个写了 `onClick` 的元素都注册一个。
- **收集并排序回调**：事件发生后，React 沿着**组件树**找到相关回调，按捕获和冒泡的顺序执行。

**为什么要收集回调？** 普通 DOM 事件直接交给浏览器处理完全可以。但 React 定义的事件传播要遵循组件树，而组件树和 DOM 树不总是一致。

例如，`App` 有一个 `onClick`，它的子组件通过 Portal 把按钮渲染到了 `App` 的 DOM 节点之外。点击按钮时，浏览器沿 DOM 树冒泡，经过不了 `App` 的 DOM 节点；React 则仍要执行 `App` 的 `onClick`。因此，React 需要根据组件关系找出沿途的回调，并决定执行顺序。

**为什么集中监听？** 它给 React 一个统一接收原生事件的入口，主要带来两类好处：

1. **减少原生监听器的注册量。** 假设一万个按钮各有一个 `onClick`：直接绑定需要约一万个原生监听器；集中监听可以只在根容器注册该类事件的监听器。**一万个业务回调依然存在**，减少的是浏览器管理的原生监听器数量及其注册、移除成本。React 官方将大型组件树的性能列为委托监听的收益，但没有说它在所有场景都更快。
2. **在子树尚未完成 hydration 时接住事件。** 页面已有服务端生成的按钮，但按钮对应的 React 代码还没接管它。根上的监听器能先发现这次点击，React 才有机会优先 hydration 相关子树并处理该事件；此时仅靠“hydration 后才装到按钮上的监听器”会漏掉这次点击。


## 二、为什么在根容器监听

React 17 以前主要委托到 `document`；改到各自的根容器后，嵌套的 React 应用以及 React 与其他代码混用时，事件可以在根之间正常停止传播。这是“选根容器而不是 `document`”的原因，和“为什么委托监听”是两个问题。

## 三、DOM 节点如何找到当前的事件回调

根容器收到点击时，可以从 `event.target` 知道用户点中了哪个 DOM 节点，但还需要找到这个节点当前的 `onClick` 函数。做法是让 DOM 节点关联它当前的 props：

```text
被点击的 DOM 节点 → 当前 props → 当前 onClick
```

先只看直接点击按钮的情况：

```jsx
<button onClick={() => setCount(count + 1)}>加一</button>
```

假设第一次渲染时 `count` 是 `0`。这次渲染产生的 `onClick` 会执行 `setCount(1)`。创建按钮 DOM 时，把包含这个回调的 props 与按钮关联起来。根容器收到点击后，就可以通过按钮找到并执行它：

```js
// 创建或更新按钮时调用
function syncProps(dom, props) {
  dom.__props = props;
}

// 此处假设 event.target 就是 button
const button = event.target;
button.__props?.onClick?.(event);
```

第一次点击后，`count` 变成 `1`，组件重新渲染。这次产生的 `onClick` 会执行 `setCount(2)`。即使按钮 DOM 没有被替换，也要用新 props 更新它的关联；否则第二次点击仍会调用旧回调，再次执行 `setCount(1)`。

## 四、如何得到捕获和冒泡顺序

从目标节点沿 `parentNode` 向根容器遍历，天然得到的是“内 → 外”。分别维护两条队列即可：

```ts
// 从目标向根容器遍历
if (typeof props?.onClickCapture === 'function') {
  capture.unshift(props.onClickCapture); // 排成外 → 内
}
if (typeof props?.onClick === 'function') {
  bubble.push(props.onClick);             // 保持内 → 外
}
```

例如外层 `div` 包着内层 `button`，点击按钮后执行顺序是：

```text
div.onClickCapture
button.onClickCapture
button.onClick
div.onClick
```

这里的重点是**收集与执行分离**：收集阶段决定有哪些回调及其顺序；执行阶段负责调用和处理中止传播。

## 五、合成事件负责统一分发控制

分发器先执行捕获队列，再执行冒泡队列。合成事件记录是否调用过 `stopPropagation()`；每次调用回调后检查该状态，停止后不再执行剩余回调。

```ts
const paths = collectPaths(nativeEvent.target, container);
const event = createSyntheticEvent(nativeEvent);

run(paths.capture, event);
if (!event.isPropagationStopped()) {
  run(paths.bubble, event);
}
```

合成事件还应把停止传播传递给原生事件。实现时直接调用 `nativeEvent.stopPropagation()`，或正确绑定其 `this`；不能随意取出方法后当普通函数调用。

## 六、完整实现流程

1. 定义支持的原生事件及其组件回调名，例如 `click → onClickCapture / onClick`。
2. 在根容器注册原生监听器，避免重复注册。
3. 创建或更新宿主 DOM 时同步最新 props。
4. 收到事件后，从目标节点向根容器遍历，生成捕获和冒泡队列。
5. 创建合成事件，依次执行两条队列，并处理停止传播。
