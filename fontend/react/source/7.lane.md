# Lane 与调度

React 用 **lane 决定本轮处理哪批更新**，再把这批工作安排到合适的时间执行。

## 1. Lane 记录待处理的工作

一次 `setState` 会创建一条更新；不同更新对响应速度的要求不同。例如，点击后的反馈需要尽快显示，`startTransition` 中耗时的界面更新可以稍后处理。如果所有更新都必须一起渲染，后者就可能拖慢前者。

因此 React 给每条 `Update` 标记 lane，并在 `FiberRoot` 上记录还有哪些 lane 待处理：**先选出本轮要渲染的更新，让更急的工作先得到处理**。同一轮可以处理多个 lane；暂时没选中的更新保留，之后再处理。lane 不只是一个优先级数字，也是用来选择一批更新的标记。

一个 `Lane` 是一个二进制位，`Lanes` 是多个位的集合。

`NoLane` / `NoLanes` 的值是 `0`，表示没有选中的 lane；`SyncLane` 等名称分别代表不同的位。

`SyncLane | DefaultLane` 表示两类更新同时等待处理。

| Lane | 含义 | 常见使用场景 | 相对优先级 |
| --- | --- | --- | --- |
| `SyncLane` | 同步更新 | 点击、按键等离散事件触发的更新，需要尽快响应。 | 1（最高） |
| `InputContinuousLane` | 连续输入更新 | 鼠标移动、滚动等连续事件触发的更新。 | 2 |
| `DefaultLane` | 普通更新 | 没有更高事件优先级时的常规状态更新，例如定时器回调中的更新。 | 3 |
| `TransitionLane` | 过渡更新（泛指过渡 lane 组） | `startTransition` 标记的界面更新，例如切换内容后渲染较大的结果区域。 | 4 |
| `IdleLane` | 空闲更新 | 空闲优先级下安排、可以继续等待的更新；常规组件更新很少用到。 | 5（最低） |

表中的数字表示相对紧急程度，**不是要求每个 lane 严格按顺序单独渲染**。例如 `SyncLane` 和 `DefaultLane` 都待处理且未暂停时，当前源码会把两者选进同一轮。

假设 `FiberRoot.pendingLanes = SyncLane | TransitionLane1`，且两类工作都可处理。React 可以先选 `SyncLane` 渲染：本轮的 `renderLanes` 是 `SyncLane`，只应用这一批更新；`TransitionLane1` 更新留在队列里，之后再调度。

| 类型字段 / 模块变量 | 含义 |
| --- | --- |
| `Update.lane` | Hook 更新队列中每条更新的 lane；创建更新节点时写入。 |
| `Fiber.lanes` | 组件 Fiber 自身待处理的 lane；入队时标记。 |
| `Fiber.childLanes` | 子树待处理的 lane；更新沿 `return` 向上冒泡时标记各祖先 Fiber。 |
| `FiberRoot.pendingLanes` | 整棵树尚未完成的 lane；`markRootUpdated` 将新 lane 加入这里。 |
| `FiberRoot.suspendedLanes` | 渲染时因等待数据而暂停的 lane；它们仍留在 `pendingLanes` 中，但不能当作普通的未暂停工作直接重试。 |
| `FiberRoot.pingedLanes` | 暂停后收到数据就绪通知、可以重新尝试的 lane。 |
| `FiberRoot.warmLanes` | 已尝试遍历的暂停 lane；选取预热工作时避免反复选择它们。 |
| `renderLanes` | `ReactFiberHooks.js` 的模块变量；`renderWithHooks` 将本轮 lane 写入，用来筛选 Hook 更新。 |
| `FiberRoot.callbackNode` | 当前安排的 Scheduler 任务节点；`scheduleCallback` 的返回值。 |
| `FiberRoot.callbackPriority` | 代表当前任务的 lane，用来判断是否复用或替换任务；不是 Scheduler priority。 |

**暂停不等于完成。**例如某轮渲染等数据时，对应 lane 仍在 `FiberRoot.pendingLanes`，同时被记入 `FiberRoot.suspendedLanes`；等数据就绪，React 将它标记到 `FiberRoot.pingedLanes`，供后续调度重试。在数据就绪前，React 也可能预热尚未尝试的部分；`FiberRoot.warmLanes` 用来避免重复预热。这些字段供第 3 节的 `getNextLanes` 判断哪些工作现在值得选。

Lane 用位运算合并和筛选：`a | b` 合并待处理工作，`(renderLanes & update.lane) === update.lane` 判断本轮是否处理某条更新。

## 2. 给更新分配 lane，并登记到 FiberRoot

`setState` 进入 `dispatchSetState` 后，先调用 `requestUpdateLane`。它只有两条主要路径：当前处于 Transition 中，就取过渡 lane；否则先取当前更新优先级，再按事件类型判断，两者都没有时，使用 `DefaultLane`。拿到 lane 后，再创建 `Update`。

```js
function dispatchSetState(fiber, queue, action) {
  const lane = requestUpdateLane(fiber);
  dispatchSetStateInternal(fiber, queue, action, lane);
}

function requestUpdateLane(fiber) {
  const transition = requestCurrentTransition();
  if (transition !== null) {
    return requestTransitionLane(transition);
  }
  return eventPriorityToLane(resolveUpdatePriority());
}
```

**先看 Transition 路径。**表格中的 `TransitionLane` 是**一组 lane 的统称**，真正写进 `Update.lane` 的是 `TransitionLane1`、`TransitionLane2` 等其中一个。它们同属过渡类别，编号主要用于区分工作，而不是新的事件优先级等级。

**为什么 Transition 需要多个 lane？**Transition 可能在 Suspense 处等待数据，React 会暂缓完成它。假设过渡 A 等待详情页数据，另一次操作产生的过渡 B 更新一个无关区域，而且 B 已经准备好。如果 A、B 固定使用同一个 lane，它们就属于同一渲染批次，A 的等待可能连 B 一起拖住。给它们不同的过渡 lane，React 才有能力在 A 等待时先完成 B；需要时仍可以把 A、B 放在同一轮处理。**目的不是强制分开，而是避免一个等待数据的过渡挡住无关的过渡。**

`SyncLane`、`InputContinuousLane`、`DefaultLane` 这类常规更新通常各用一个 lane：它们遇到悬挂时通常及时显示 fallback，而不是为了等数据一直保留这批渲染。同类更新合批可以减少重复渲染和提交后的布局、绘制开销。Transition 可能选择等待数据，所以才需要多个 lane 来避免无关的等待互相拖住。

`requestTransitionLane` 因此缓存本次事件选中的 lane，让同一事件的后续过渡更新复用它；下次需要新 lane 时再从过渡 lane 组轮流取。若异步 Action 已关联 lane，也复用它。

```js
let currentEventTransitionLane = NoLane;
let nextTransitionUpdateLane = TransitionLane1;

const TransitionUpdateLanes =
  TransitionLane1 | TransitionLane2 | TransitionLane3 | TransitionLane4 |
  TransitionLane5 | TransitionLane6 | TransitionLane7 | TransitionLane8 |
  TransitionLane9 | TransitionLane10;

function requestTransitionLane(transition) {
  // transition 参数表明调用方已确认当前处于 Transition 中。
  if (currentEventTransitionLane === NoLane) {
    const actionScopeLane = peekEntangledActionLane();
    currentEventTransitionLane = actionScopeLane !== NoLane
      ? actionScopeLane
      : claimNextTransitionUpdateLane();
  }
  return currentEventTransitionLane;
}

function claimNextTransitionUpdateLane() {
  const lane = nextTransitionUpdateLane;
  nextTransitionUpdateLane <<= 1;
  if ((nextTransitionUpdateLane & TransitionUpdateLanes) === NoLanes) {
    nextTransitionUpdateLane = TransitionLane1;
  }
  return lane;
}
```

`TransitionUpdateLanes` 是可分配的过渡更新 lane 集合；`nextTransitionUpdateLane` 指向下次分配的位置。根调度微任务结束时清空 `currentEventTransitionLane`，下次事件再重新选。

**再看普通更新路径。**`resolveUpdatePriority` 先取 React 当前设置的更新优先级；没有时根据当前事件类型判断。`getEventPriority` 在这里仅列常见事件。

```js
// 事件优先级常量与对应 lane 同值。
const DiscreteEventPriority = SyncLane;
const ContinuousEventPriority = InputContinuousLane;
const DefaultEventPriority = DefaultLane;
const IdleEventPriority = IdleLane;

function resolveUpdatePriority() {
  const priority = getCurrentUpdatePriority();
  if (priority !== NoEventPriority) return priority;
  if (window.event === undefined) return DefaultEventPriority;
  return getEventPriority(window.event.type);
}

function getEventPriority(type) {
  if (type === 'click' || type === 'keydown') return DiscreteEventPriority;
  if (type === 'mousemove' || type === 'scroll') return ContinuousEventPriority;
  return DefaultEventPriority;
}

function eventPriorityToLane(priority) {
  return priority;
}
```

因此点击得到 `SyncLane`，鼠标移动得到 `InputContinuousLane`，没有当前事件的普通更新得到 `DefaultLane`。点击回调中的 `startTransition` 更新走前面的 Transition 路径，得到过渡 lane。

**最后登记更新。**`dispatchSetStateInternal` 创建带有 `lane` 的 `Update` 并入队；`scheduleUpdateOnFiber` 把 lane 加进 `FiberRoot.pendingLanes`，再安排根调度检查。

```js
function dispatchSetStateInternal(fiber, queue, action, lane) {
  const update = {lane, action, next: null};
  const root = enqueueConcurrentHookUpdate(fiber, queue, update, lane);
  if (root !== null) {
    scheduleUpdateOnFiber(root, fiber, lane);
  }
}

function scheduleUpdateOnFiber(root, fiber, lane) {
  markRootUpdated(root, lane); // root.pendingLanes |= lane
  ensureRootIsScheduled(root); // 将 root 放进待调度链表，并安排微任务
}
```

到这里**还没有执行 render**；只是给更新定了 lane，并告诉 `FiberRoot` 有这类工作待处理。

## 3. 选本轮 lane，并安排执行

上一节把更新的 lane 登记到 `FiberRoot.pendingLanes`，并安排了根调度微任务。接下来只有一条主线：**从待处理 lane 中选出这次要做的工作 → 判断是否继续上次未完成的渲染 → 安排执行 → 进入 render**。

`getNextLanes` 负责前两步。参数 `root` 是 `FiberRoot`；`wipLanes` 是上次渲染尚未完成时所用的 lanes，没有则是 `NoLanes`；`rootHasPendingCommit` 表示已有等待完成的提交。`getHighestPriorityLanes` 从候选中取一批 lane，不一定只返回一个位。

```js
function getNextLanes(root, wipLanes, rootHasPendingCommit) {
  const pending = root.pendingLanes;
  if (pending === NoLanes) return NoLanes;

  // 有非空闲工作时先处理它们；只有非空闲工作全部完成，IdleLane 才进入候选。
  const nonIdle = pending & NonIdleLanes;
  const candidates = nonIdle !== NoLanes ? nonIdle : pending;

  // 先选未暂停的工作；没有时重试已被唤醒的工作。
  let available = candidates & ~root.suspendedLanes;
  if (available === NoLanes) available = candidates & root.pingedLanes;
  if (available === NoLanes && !rootHasPendingCommit) {
    available = candidates & ~root.warmLanes; // 都不能直接做时，尝试预热。
  }
  if (available === NoLanes) return NoLanes;
  const nextLanes = getHighestPriorityLanes(available);

  // 已有渲染未完成时，只有值得打断它才切换到 nextLanes。
  if (wipLanes !== NoLanes && wipLanes !== nextLanes &&
      (wipLanes & root.suspendedLanes) === NoLanes) {
    const nextLane = getHighestPriorityLane(nextLanes);
    const wipLane = getHighestPriorityLane(wipLanes);
    if (nextLane >= wipLane ||
        (nextLane === DefaultLane && (wipLane & TransitionLanes) !== NoLanes)) {
      return wipLanes;
    }
  }
  return nextLanes;
}
```

读这段代码只抓住两点：`pending = IdleLane` 时，`nonIdle` 为零，所以候选就是 `IdleLane`；只要还有任何非空闲待处理工作，Idle 就不会被选。`nextLanes` 可以是一批，例如 `SyncLane | DefaultLane` 会一起返回。最后返回 `wipLanes` 表示继续旧渲染，返回 `nextLanes` 表示处理新选出的工作；其中 `DefaultLane` 不打断正在渲染的 Transition。


根调度微任务对每个待调度的 `FiberRoot` 调用 `scheduleTaskForRootDuringMicrotask`。**这个函数只安排工作，不在这里渲染。**它按刚选出的 lane 分成两条路径：

```js
function scheduleTaskForRootDuringMicrotask(root) {
  const wipLanes = root === getWorkInProgressRoot()
    ? getWorkInProgressRootRenderLanes() : NoLanes;
  const rootHasPendingCommit =
    root.cancelPendingCommit !== null || root.timeoutHandle !== noTimeout;
  const nextLanes = getNextLanes(root, wipLanes, rootHasPendingCommit);
  if (nextLanes === NoLanes) return NoLane;

  if (includesSyncLane(nextLanes)) {
    // 先记下有同步工作；微任务末尾统一执行，不创建 Scheduler 任务。
    cancelCallback(root.callbackNode);
    root.callbackPriority = SyncLane;
    root.callbackNode = null;
    return SyncLane;
  }

  const callbackPriority = getHighestPriorityLane(nextLanes);
  if (root.callbackPriority === callbackPriority) return callbackPriority;
  cancelCallback(root.callbackNode);

  const eventPriority = lanesToEventPriority(nextLanes);
  const schedulerPriority =
    eventPriority === IdleEventPriority ? IdleSchedulerPriority :
    eventPriority === DefaultEventPriority ? NormalSchedulerPriority :
    UserBlockingSchedulerPriority;

  root.callbackNode = scheduleCallback(
    schedulerPriority,
    performWorkOnRootViaSchedulerTask.bind(null, root),
  );
  root.callbackPriority = callbackPriority;
  return callbackPriority;
}
```

`callbackPriority` 是代表这批工作的 lane，用于决定是否复用已有任务；`schedulerPriority` 决定这项工作进入 Scheduler 队列后的执行先后。

根调度微任务最后执行同步工作；非同步工作则等 Scheduler 后续调用刚才传入的 `performWorkOnRootViaSchedulerTask`：

```js
function processRootScheduleInMicrotask() {
  let root = firstScheduledRoot;
  while (root !== null) {
    scheduleTaskForRootDuringMicrotask(root); // 为每个 FiberRoot 选 lane 并安排任务
    root = root.next;
  }
  flushSyncWorkAcrossRoots_impl(NoLanes, false); // 微任务末尾执行 SyncLane
}

function performWorkOnRootViaSchedulerTask(root, didTimeout) {
  const wipLanes = root === getWorkInProgressRoot()
    ? getWorkInProgressRootRenderLanes() : NoLanes;
  const rootHasPendingCommit =
    root.cancelPendingCommit !== null || root.timeoutHandle !== noTimeout;
  const lanes = getNextLanes(root, wipLanes, rootHasPendingCommit); // 执行前重新选
  const forceSync = !disableSchedulerTimeoutInWorkLoop && didTimeout;
  if (lanes !== NoLanes) performWorkOnRoot(root, lanes, forceSync); // 进入 render
}
```

因此“何时执行”分两条：含 `SyncLane` 的工作在**根调度微任务末尾**进入 render；其他工作由 `scheduleCallback` 放进 Scheduler，等**后续宿主任务轮到它时**进入 render。Scheduler 在浏览器中通常用 `MessageChannel` 请求宿主任务；没有固定的等待毫秒数，也不保证浏览器先绘制。

## 4. 任务开始后，渲染仍按 lane 筛选更新

Scheduler 执行 `performWorkOnRootViaSchedulerTask` 时会**重新调用 `getNextLanes`**，因为等待期间可能有新更新。随后 `performWorkOnRoot` 决定这次 render 能否分段：

```js
function performWorkOnRoot(root, lanes, forceSync) {
  const shouldTimeSlice =
    !forceSync &&
    !includesBlockingLane(lanes) &&
    !includesExpiredLane(root, lanes);

  if (shouldTimeSlice) renderRootConcurrent(root, lanes);
  else renderRootSync(root, lanes);
}
```

因此，**交给 Scheduler 不等于一定时间切片**。`DefaultLane` 通常是 Scheduler 的 Normal priority 任务，但 render 通常连续完成；过渡 lane 通常也是 Normal priority 任务，却可以在 Fiber 工作单元之间让出。

组件处理 Hook 队列时，`updateReducerImpl` 用本轮的 `renderLanes` 判断每条更新：匹配就计算新 state，不匹配就留在 `baseQueue` 等后续渲染。提交后，`markRootFinished` 更新 `FiberRoot.pendingLanes`，未完成的 lane 继续等待调度。

```js
function updateReducerImpl(updates, renderLanes, baseState, reducer) {
  let newState = baseState;
  for (const update of updates) {
    if ((renderLanes & update.lane) !== update.lane) {
      // 本轮不处理；源码将它保留在 baseQueue。
      continue;
    }
    newState = reducer(newState, update.action);
  }
  return newState;
}
```

这也解释了 `useTransition`：回调内的 `setState` 被分到 `TransitionLane`，`isPending = true` 的乐观更新在 `SyncLane`，所以它们可以分批处理。
