# Suspense：渲染等待与展示边界

Suspense 表达一条展示规则：某块内容在渲染时发现依赖尚未就绪，就先展示备用内容；依赖就绪后，React 再尝试渲染真正的内容。

```jsx
<Suspense fallback={<Loading />}>
  <Product />
</Suspense>
```

- `children`：希望展示的真实内容，这里是 `Product`。
- `fallback`：等待期间展示的备用内容，这里是 `Loading`。
- 边界：这个 Suspense 在组件树中负责的区域。

Suspense 管理等待期间的展示；资源加载由 `lazy`、数据层等负责。

## 1. 边界什么时候生效

需要区分“定义边界”和“启用 fallback”：

1. 在组件树里写下 `<Suspense>`，定义等待时由哪个边界负责。
2. React 渲染它的后代时，读取到尚未就绪的依赖，发生 suspension。
3. React 找到最近的上层 Suspense，处理这个区域的等待状态。

首次展示内容时，典型流程是：

```text
React 尝试渲染组件
  → 读取渲染所需的依赖
  → 依赖尚未就绪，当前渲染无法完成
  → 最近的上层 Suspense 展示 fallback
  → 依赖就绪，React 安排重试渲染
  → 渲染完成并提交，展示真实内容
```

触发点是“渲染时读取到尚未就绪的依赖”。创建 Promise、开始请求，本身不会触发 Suspense。

这里的“暂停”指当前渲染暂时无法完成。JavaScript 线程仍然可以处理其他工作；重试时，组件的渲染逻辑可能再次执行。

## 2. 两种最常用的触发场景

### 2.1 lazy：等待组件代码

`App.jsx`：

```jsx
import { lazy, Suspense } from 'react';

// 声明懒加载组件，真正尝试渲染时才调用加载函数。
const Product = lazy(() => import('./Product.jsx'));

export default function App() {
  return (
    <>
      <h1>商城</h1>
      <Suspense fallback={<p>代码加载中……</p>}>
        <Product />
      </Suspense>
    </>
  );
}
```

`Product.jsx`：

```jsx
export default function Product() {
  return <h2>机械键盘</h2>;
}
```

执行 `lazy(...)` 只是声明组件。React 首次尝试渲染 `<Product />` 时，才调用 `() => import('./Product.jsx')`。

如果组件代码尚未加载完成，这次渲染就发生 suspension，商品区域先显示“代码加载中……”。代码就绪后，React 重试并展示“机械键盘”。

`lazy` 应声明在组件外部。它会缓存加载函数返回的 Promise 和加载结果；这个例子中的模块需要默认导出组件。

参考：[React lazy 文档](https://react.dev/reference/react/lazy)。

### 2.2 use：等待 Promise 的结果

下面是 React 19 客户端示例，用延迟模拟数据请求：

```jsx
import { Suspense, use } from 'react';

// 在渲染前创建，并复用同一个 Promise；仅用于浏览器端教学。
const productPromise = new Promise((resolve) => {
  setTimeout(() => {
    resolve({ name: '机械键盘' });
  }, 1500);
});

function Product() {
  const product = use(productPromise);

  return <h2>{product.name}</h2>;
}

export default function App() {
  return (
    <Suspense fallback={<p>数据加载中……</p>}>
      <Product />
    </Suspense>
  );
}
```

Promise 创建后，模拟请求已经开始。React 渲染 `Product`，执行 `use(productPromise)` 时，才根据 Promise 的状态决定后续行为：

| Promise 状态 | 渲染时读取的行为 |
| --- | --- |
| pending | 发生 suspension，由上层 Suspense 处理等待状态 |
| fulfilled | 返回结果，组件继续生成 UI |
| rejected | 抛出失败原因，由上层 Error Boundary 处理 |

关键是通过 `use` 或支持 Suspense 的数据层读取结果。普通 Promise 不会自动让组件 suspend。

同一资源在渲染重试时，应复用同一个 Promise。直接在渲染中调用 `use(fetch(...))` 会不断创建新的 Promise，可能导致重复请求和持续等待。实际项目通常由数据层管理缓存和失效。

参考：[React use 文档](https://react.dev/reference/react/use)。

## 3. 为什么称为边界

边界的位置决定哪块内容在等待，以及哪些内容一起出现。

```jsx
<>
  <h1>商城</h1>
  <Suspense fallback={<p>商品加载中……</p>}>
    <Product />
  </Suspense>
</>
```

标题在边界外，商品首次加载时，标题可以先出现，商品区域显示 fallback。

```jsx
<Suspense fallback={<p>页面加载中……</p>}>
  <h1>商城</h1>
  <Product />
</Suspense>
```

标题和商品在同一个边界内。商品首次渲染发生 suspension 时，这整个区域先显示 fallback，标题也一起等待。

同理，商品和评论分别放在两个边界里，可以各自展示；放在同一个边界里，就作为一组展示。边界应对应希望用户感受到的加载区域。

## 4. 容易混淆的地方

- `useEffect` 中的普通请求不会自动触发 Suspense：组件已经正常返回 JSX，没有在渲染时报告 suspension。
- 边界必须在发生 suspension 的组件上方：组件先调用 `use`，再在返回的 JSX 中写 Suspense，处理不了前面那次 suspension。
- 发生 suspension 不等于立即显示 fallback：首次加载通常展示 fallback；已经展示过内容的区域，在 Transition 等更新中可以继续保留旧内容。
- Promise 就绪不等于屏幕立即更新：React 还需要重试渲染、完成提交，浏览器再绘制。
- Suspense 的 loading fallback 不负责客户端错误处理：失败需要 Error Boundary。
- 增加边界不会自动让请求并行：请求何时开始、是否相互依赖，仍由加载逻辑决定。

判断一个场景时，沿着这条链检查：

```text
资源何时开始加载
  → 渲染时如何读取
  → 是否发生 suspension
  → 最近的上层边界在哪里
  → 等待期间展示什么
  → 就绪后如何重试并提交
```

参考：[React Suspense 文档](https://react.dev/reference/react/Suspense)。
