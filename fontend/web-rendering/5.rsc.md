# RSC：React 服务端组件

RSC 是 React Server Components，通常译为“React 服务端组件”。它让服务端先执行一部分 React 组件，把这些组件计算出的 UI 描述交给客户端 React；客户端结合自己的组件代码，继续完成页面渲染和交互。

理解 RSC，需要分清三个东西：

- 组件定义：接收 props、返回 JSX 的函数代码。
- 组件输出：执行组件后得到的 React 元素结构。
- 页面 HTML：把元素结构转换成的 HTML，属于另一阶段的产物。

RSC 允许浏览器接收某些组件的输出，而无需下载、执行这些组件的函数。服务端组件输出通过 Flight 协议传输；它可以继续参与 SSR，也可以直接交给浏览器中的 React 渲染。

本文先沿着一条主线理解 RSC：为什么移动组件计算 → 服务端执行哪些函数 → Flight 表达什么 → 浏览器接着做什么。最后再对照 SSR、CSR，区分组件执行、代码下载和 HTML 生成。

## 1. 为什么需要 RSC

假设商品页面包含商品数据、Markdown 介绍和一个交互按钮。

采用客户端渲染时，典型流程是：

```text
浏览器下载组件及依赖
  → 执行组件，发起商品请求
  → 获得数据
  → 解析 Markdown、处理内容
  → 生成元素并创建 DOM
```

用户只需要看到处理好的介绍，却可能还要下载处理介绍的代码。页面数据如果由父子组件逐级请求，还可能经历多次浏览器与服务器之间的往返。

RSC 提供另一种分工：

```text
服务端读取商品
  → 服务端执行组件，处理介绍并组织 UI
  → 把结果交给浏览器
  → 浏览器显示内容，执行交互组件
```

两种方式的区别，不只是接口返回位置不同，而是交给浏览器的内容不同：

| 方式 | 服务端提供什么 | 浏览器还要做什么 |
| --- | --- | --- |
| 数据接口配合客户端组件 | 商品数据，例如名称、介绍 | 执行商品组件，把数据组织成元素 |
| RSC | 服务端组件计算出的元素结构、数据和客户端组件引用 | 使用这些结果，执行其中的客户端组件 |

移动到服务端的是一部分组件计算和依赖，而不仅是数据请求的位置。只被服务端代码使用的 Markdown 解析、高亮等依赖可以留在服务端；如果它们也被客户端模块引用，则仍可能进入客户端包。

RSC 能减少某些浏览器与服务器之间的往返，但不会自动消除顺序依赖，也不代表所有数据都应该由服务端组件读取。

参考：[React Server Components](https://react.dev/reference/rsc/server-components)。

## 2. 用一个商品组件理解分工

下面假设项目已经支持 RSC，`loadProduct` 是现有的数据读取函数。示例说明组件分工，不包含路由、构建和网络端点的完整实现。

`Product.jsx`：

```jsx
import { loadProduct } from './product-data.js';
import BuyButton from './BuyButton.jsx';

export default async function Product({ id }) {
  // 在服务端读取商品，数据层可以访问数据库或已有服务。
  const product = await loadProduct(id);

  return (
    <section>
      <h1>{product.name}</h1>
      <ProductDescription text={product.description} />
      <BuyButton productId={product.id} />
    </section>
  );
}

function ProductDescription({ text }) {
  return <p>{text}</p>;
}
```

`BuyButton.jsx`：

```jsx
'use client';

import { useState } from 'react';

export default function BuyButton({ productId }) {
  const [quantity, setQuantity] = useState(1);

  return (
    <button onClick={() => setQuantity(value => value + 1)}>
      商品 {productId}，购买数量 {quantity}
    </button>
  );
}
```

这里的按钮仅演示客户端状态更新，不包含下单操作。

| 组件 | 本例中的执行分工 | 原因 |
| --- | --- | --- |
| `Product` | 服务端组件 | 读取商品，组织页面结构 |
| `ProductDescription` | 服务端组件 | 把介绍转换为元素，无需客户端状态 |
| `BuyButton` | 客户端组件 | 使用 `useState`，响应 `onClick` |

服务端组件仍然遵循“props 输入，UI 输出”的组件接口，但不能拥有 `useState`、`useEffect` 这样的客户端状态与生命周期，也不能定义需要在浏览器触发的事件处理函数。

## 3. 服务端如何生成 RSC 输出

假设 `loadProduct(42)` 返回：

```js
{
  id: 42,
  name: '机械键盘',
  description: '支持自定义按键的机械键盘。'
}
```

服务端 RSC 渲染过程是：

```text
收到 Product 元素及 props：id = 42
  → 执行 Product，等待商品数据
  → 处理 Product 返回的元素结构
  → 执行 ProductDescription，得到 p 元素
  → 保留 section、h1、p 及其 props
  → 遇到 BuyButton，记录客户端组件引用及 props
  → 编码并输出 Flight
```

不同节点的处理方式不同：

| 遇到的节点 | RSC 渲染阶段如何处理 |
| --- | --- |
| 服务端组件 | 执行它，继续处理它返回的结果 |
| 原生元素，如 `section`、`h1` | 保留元素类型、props、children |
| 客户端组件 | 保留组件引用与 props，交给后续渲染阶段 |

在 RSC 渲染阶段，React 不执行 `BuyButton` 的组件函数，因此这一阶段还没有算出按钮内部的文字和元素。服务端记录的是“后续使用 BuyButton，传入 productId = 42”。

如果随后采用 SSR，`BuyButton` 会在 SSR 阶段执行；如果直接交给浏览器渲染，则在浏览器执行。不能把“RSC 阶段不执行”理解成“整个服务端永远不执行客户端组件”。

最终输出在概念上相当于：

```jsx
<section>
  <h1>机械键盘</h1>
  <p>支持自定义按键的机械键盘。</p>
  <BuyButton productId={42} />
</section>
```

这只是便于阅读的表达，实际网络传输使用 Flight。浏览器收到的结构无需再调用 `Product` 和 `ProductDescription`；它们已经由执行后的元素输出替代。

Flight 在处理组件树的过程中产生，而不是必须等整棵树完成后才一次性生成。已完成的部分可以先发送，异步等待的子树随后补充；配合 Suspense 可以组织等待体验。生成发生在构建期间还是请求期间、通过哪个端点传输，由项目的集成方式决定。

参考：[RSC RFC 渲染流程](https://github.com/reactjs/rfcs/blob/main/text/0188-server-components.md#simplified-loading-sequence)。

## 4. Flight 传什么，浏览器如何使用

Flight 表达的是 React UI 描述，包括元素、数据、客户端组件引用等信息。下面是教学示意，不是实际 Flight 字节格式，也不是可以直接运行的 React 对象：

```js
{
  type: 'section',
  props: {
    children: [
      {
        type: 'h1',
        props: { children: '机械键盘' }
      },
      {
        type: 'p',
        props: { children: '支持自定义按键的机械键盘。' }
      },
      {
        type: {
          kind: 'client-reference',
          module: './BuyButton.jsx',
          export: 'default'
        },
        props: { productId: 42 }
      }
    ]
  }
}
```

| 信息 | 来源 | 用途 |
| --- | --- | --- |
| `section`、`h1`、`p` | 服务端组件输出 | 描述生成什么元素 |
| 文本、`children` | 商品数据与返回的 JSX | 表达内容及嵌套关系 |
| 客户端组件引用 | `BuyButton` 的导入与构建工具映射 | 找到对应模块和导出 |
| `productId: 42` | 服务端传入的 props | 为客户端组件提供输入 |

JavaScript 函数不能直接从服务器内存搬到浏览器内存。构建工具建立模块映射，让服务端可以描述“这里使用哪个客户端组件”，客户端运行环境再找到相应代码。实际模块标识和资源地址由集成方式决定，不一定是示意中的源码路径。

浏览器使用这些信息的过程是：

```text
接收 Flight
  → React 解码器恢复元素结构与客户端组件引用
  → 配合加载的 BuyButton 模块
  → React 执行 BuyButton，组合页面
  → 创建 DOM，或接管 SSR 已生成的 DOM
```

注意“恢复元素结构”和“重新执行服务端组件”是两回事。解码后的树包含 `section`、`h1`、`p` 和 `BuyButton` 的引用；浏览器无需拥有 `Product`、`ProductDescription` 的函数代码。

因此，浏览器继续执行 `BuyButton` 时，商品名称和介绍已经是具体内容。React 不是重新查询商品再算一遍整个页面，而是把服务端输出与客户端组件的输出组合起来。

Flight 不是 HTML，浏览器不能直接把它当成页面标记解析；它需要 React 解码和渲染。它也不是服务端组件源码，浏览器不会通过它恢复并执行 `Product` 函数。

## 4. RSC 与 SSR、CSR 的关系

先分清两类问题：RSC 划分组件执行与代码交付的边界；SSR、CSR 讨论页面内容是在服务端提前生成 HTML，还是由浏览器执行 JavaScript 创建 DOM。它们可以组合。

| 机制 | 做什么 | 产物 |
| --- | --- | --- |
| CSR | 浏览器执行 React 渲染，创建或更新 DOM | DOM |
| SSR | 服务端执行 React 渲染，提前生成页面 HTML | HTML |
| RSC | 服务端执行 Server Components，保留客户端组件引用 | Flight |

浏览器最终都会解析、布局、绘制页面。SSR 指服务端提前生成 HTML，不是服务端替浏览器画屏幕。

### 4.1 普通 CSR 和普通 React SSR 执行哪些函数

下面对照相同商品页面在不同架构下的数据流，组件实现需要相应调整。前面的 `async Product` 是 RSC 示例，不能原样作为客户端组件使用。

以下“普通 CSR”“普通 React SSR”均不使用 RSC，并假设商品页的全部组件都参与客户端运行。此时 `Product`、`ProductDescription`、`BuyButton` 都需要交给浏览器。

普通 CSR 的流程是：

```text
下载 Product、ProductDescription、BuyButton 的代码及依赖
  → 获得商品数据
  → 浏览器执行 Product、ProductDescription、BuyButton
  → 创建 DOM
```

普通 React SSR 则先生成 HTML，再由客户端接管：

```text
服务端执行 Product、ProductDescription、BuyButton
  → 返回 HTML，浏览器先显示内容
  → 下载 Product、ProductDescription、BuyButton 的代码及依赖
  → 浏览器执行这些组件进行 hydration，接管已有 DOM
  → 后续交互在浏览器执行
```

SSR 提前提供 HTML，但本例中的三个组件仍需要在浏览器运行。服务端已经执行过组件，不代表浏览器可以省掉这些组件代码。

这里的两次组件执行分别发生在服务端和浏览器。服务端运行出的 HTML 可以提前显示；浏览器运行组件以建立客户端 React 树，接管已有 DOM。服务端事件处理函数不会随 HTML 自动变成浏览器事件监听器。

### 4.2 RSC 输出直接交给浏览器

```text
服务端：执行 Product、ProductDescription → Flight

浏览器：
  解码 Flight + 加载 BuyButton 的代码及其客户端依赖
    → 执行 BuyButton，结合服务端已经生成的元素结构
    → React 创建 DOM
    → 持续处理交互
```

这种方式没有通过 SSR 提前生成商品 HTML，但已经让 `Product`、`ProductDescription` 的代码及其专属依赖留在服务端。可以将其理解为“RSC + 客户端 DOM 渲染”：最终由浏览器创建 DOM，不代表所有组件函数都在浏览器执行。

### 4.3 RSC 配合 SSR

```text
服务端：
  RSC 阶段：执行 Product、ProductDescription
    → 生成元素结构及 BuyButton 引用和 props
    → SSR 阶段：使用上述结果，执行 BuyButton
    → 将组合后的树生成 HTML

浏览器收到：
  HTML + Flight + 客户端组件 JavaScript

浏览器：
  先显示 HTML
    → 解码 Flight，加载 BuyButton 的代码及其客户端依赖
    → 执行 BuyButton 进行 hydration，接管交互
```

这表示阶段之间的数据依赖；实际传输可以流式进行，不要求等待完整 Flight 后才开始 SSR。

这里不是“RSC 执行一次 Product，SSR 再执行一次 Product”。对于这份已经生成的 RSC 输出，SSR 使用其中的元素结构，只继续执行尚未展开的客户端组件；浏览器也使用服务端输出，不重新调用 `Product`、`ProductDescription`。

| RSC 配合 SSR 的阶段 | 执行哪些组件函数 | 得到什么 |
| --- | --- | --- |
| 服务端 RSC | `Product`、`ProductDescription` | 商品元素结构、`BuyButton` 引用及 props |
| 服务端 SSR | `BuyButton` | 基于商品结构和按钮输出生成 HTML |
| 浏览器 hydration | `BuyButton` | 建立客户端运行状态，接管已有 DOM |

表格描述各阶段负责执行的组件，不承诺组件函数总共只被调用一次。它解释的是渲染分工，而不是用来统计开发模式、重试或重新请求时的调用次数。
