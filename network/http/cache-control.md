# Cache-Control

`Cache-Control` 是 HTTP 请求头和响应头，用来控制响应能否保存、由谁保存、多久可以直接复用，以及过期后如何处理。多个指令用逗号分隔，先区分请求与响应、浏览器与共享缓存，再判断各条规则。

## 1. 先建立运行模型

HTTP 缓存保存的是响应，包括**状态码、可保存的响应头和响应体**。

```text
浏览器的私有缓存 → CDN / 代理的共享缓存 → 源服务器
```

浏览器本地命中时，可以不发网络请求；本地未命中时，请求可能由 CDN 满足，仍然不需要访问源服务器。因此，“发了网络请求”和“访问了源服务器”不是一回事。

| 概念                 | 含义                                                   |
| -------------------- | ------------------------------------------------------ |
| 私有缓存             | 专属于某个用户的缓存，典型是浏览器 HTTP 缓存           |
| 共享缓存             | 可以供多个用户复用的缓存，典型是 CDN、缓存代理         |
| 新鲜（fresh）        | 按当前策略仍处于新鲜期；没有额外限制时可以直接复用     |
| 过期（stale）        | 已超出新鲜期；不等于删除，也不代表内容一定变化         |
| 验证（revalidation） | 向服务器确认已有副本是否还能使用，通常通过条件请求完成 |

常说的“强缓存”是直接复用本地响应；“协商缓存”是通过网络验证后复用。过期的响应可以继续保存，供后续验证使用。

## 2. 响应指令：服务器规定缓存策略

### 2.1 max-age=N：新鲜期为 N 秒

```http
Cache-Control: max-age=600
```

假设响应在 12:00 生成后立即收到：12:05 再次请求，无其他限制时可直接使用缓存；12:11 缓存已过期。过期后按其他缓存指令处理；没有额外指令时，联网先验证或重新获取，断网允许使用旧副本。

**`max-age` 按响应已经经过的累计时间计时；读取缓存或把缓存传给浏览器，都不会重新计时。**

- `Date`：这条响应报文在源站生成的时间，不是文件的最后修改时间。
- `Age`：缓存估计这份响应距源站生成或成功验证已过多少秒，包含此前在上游缓存和传输中经过的时间。

以 Chrome/Chromium 为例，分别计算 `max(0, 收到时间 − Date)` 和 `Age + 请求耗时`，取较大值，再加上收到后本地经过的时间，就是当前缓存年龄。源站验证成功后，按更新后的 `Date`、`Age` 和缓存策略重新计算年龄及新鲜期。

### 2.2 no-cache：可以存，每次复用前都要验证

`no-cache` 只要求验证，验证依据通常由 `ETag` 或 `Last-Modified` 提供；浏览器下次分别带上 `If-None-Match` 或 `If-Modified-Since` 发条件请求，没有可用验证器时则重新获取完整响应。

```http
Cache-Control: no-cache
ETag: "article-v1"
```

第一次下载后，浏览器可以保存正文和 `ETag`。下次需要复用时，发送：

```http
GET /article HTTP/1.1
Host: example.com
If-None-Match: "article-v1"
```

- 内容没变：服务器返回 `304 Not Modified`，不再传输正文，浏览器复用已有正文并更新缓存元数据。
- 内容变了：服务器返回 `200 OK`，传输新正文和相应的验证信息。
- 没有可用验证器，或者服务器不支持条件请求：可能重新下载完整响应。

`no-cache` 禁止未经验证就复用，不禁止存储；它可以节省正文传输，但仍然需要网络验证。

### 2.3 no-store：不保存本次内容供后续请求复用

```http
Cache-Control: no-store
```

要求私有缓存和共享缓存都不要存储本次请求、响应，也不能用这份响应满足其他请求。例如一次性敏感内容不希望被 HTTP 缓存保存，可以声明该指令。

它不是清除所有历史副本的命令，也不控制应用自己保存到数据库、LocalStorage 等位置的数据。`must-understand` 的特殊组合见后文。

| 配置        | 可以保存本次响应吗 | 后续复用方式                                           |
| ----------- | ------------------ | ------------------------------------------------------ |
| `no-cache`  | 可以               | 先验证，成功后复用                                     |
| `no-store`  | 不可以             | 不依赖本次响应的 HTTP 缓存复用                         |
| `max-age=0` | 可以               | 立即过期，通常需要验证；单独使用不等于严格禁止过期兜底 |

### 2.4 public / private：控制谁能保存

**它们控制的是“哪类 HTTP 缓存可以保存响应”。浏览器内置的 HTTP 缓存通常属于私有缓存，CDN、缓存代理属于共享缓存。两者的主要区别在于是否允许共享缓存保存整份响应。**

| 响应指令 | 浏览器私有缓存 | CDN、代理等共享缓存 |
| --- | --- | --- |
| `public` | 允许保存 | 允许保存 |
| `private` | 允许保存 | 禁止保存整份响应 |

这里的“共享”是指响应可以供不同用户的请求复用；同一浏览器多个标签页复用本地缓存，仍属于私有缓存。`public` 不会把浏览器缓存变成共享缓存，`private` 也不会自动按网站登录账号隔离浏览器缓存。

```http
Cache-Control: public, max-age=600
```

例如公开文章：浏览器可以保存，CDN 也可以保存一份供不同用户复用；这里的新鲜期是 600 秒。已经按其他规则可缓存的普通响应，不一定必须额外写 `public`。

```http
Cache-Control: private, max-age=60
```

例如个人资料：浏览器可以保存 60 秒，CDN 不能保存整份响应后供其他用户复用。因此，`private` 不等于禁止浏览器缓存，也不承担加密或身份认证功能。

`public/private` 本身不规定缓存多久，也不强制缓存必须保存。还要结合其他指令：例如 `public, no-store` 仍禁止存储，不能因为有 `public` 就允许保存。[规范说明](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7)

### 2.5 s-maxage=N：覆盖共享缓存的新鲜期

```http
Cache-Control: public, max-age=60, s-maxage=600
```

- 浏览器忽略 `s-maxage`，按 `max-age=60` 判断新鲜期。
- CDN 等共享缓存按 `s-maxage=600` 判断新鲜期，覆盖这里的 `max-age`。

响应年龄为 120 秒时，浏览器缓存已经过期；但请求仍可能由新鲜的 CDN 缓存满足。浏览器从 CDN 收到响应时，还要考虑 `Age`，不会自动获得一个全新的 60 秒窗口。

`s-maxage` 还包含 `proxy-revalidate` 语义：按 HTTP 核心规范，共享缓存过期后，成功验证前不能复用旧响应。

### 2.6 must-revalidate / proxy-revalidate：约束过期后的复用

```http
Cache-Control: max-age=600, must-revalidate
```

600 秒新鲜期内可以直接用；正常联网时，只有 `max-age=600` 也会在过期后验证或重新获取。`must-revalidate` 额外禁止过期后未经成功验证就用旧副本兜底：例如第 700 秒断网，只有 `max-age=600` 时允许返回旧副本；加上 `must-revalidate` 后只能返回错误，不能直接使用旧副本。

| 指令               | 何时必须验证             | 作用范围           |
| ------------------ | ------------------------ | ------------------ |
| `no-cache`         | 每次复用前，包括新鲜期内 | 私有缓存、共享缓存 |
| `must-revalidate`  | 过期后复用前             | 私有缓存、共享缓存 |
| `proxy-revalidate` | 过期后复用前             | 仅共享缓存         |

`max-age=0, must-revalidate` 在常见复用场景中的效果接近 `no-cache`；需要每次验证时，直接表达为 `no-cache` 更清楚。

### 2.7 immutable：新鲜期内同一 URL 的内容不会变

```http
Cache-Control: public, max-age=31536000, immutable
```

`31536000` 秒为 365 天。平时访问时，只有 `max-age` 也能直接使用新鲜缓存；区别主要在普通刷新：例如缓存还剩 500 秒，只有 `max-age` 时可能仍会验证，加上 `immutable` 就明确承诺新鲜期内内容不变，支持它的浏览器可以省掉这次验证。

`immutable` 不延长新鲜期，过期后不再生效，强制刷新仍可绕过它。Chrome 对普通刷新的子资源本来就有跳过验证的优化，所以加上它不一定产生额外变化。[浏览器说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#avoiding_revalidation)

例如 `/assets/app.a81f3c.js` 长期缓存；内容变化后发布成 `/assets/app.b92d4e.js`，页面引用新的 URL，浏览器便会获取新文件。一直覆盖同一个 URL，却声明一年不变，可能导致用户长期看到旧版本。

### 2.8 stale-while-revalidate=N：过期窗口内先返回旧响应，后台更新

```http
Cache-Control: max-age=60, stale-while-revalidate=30
```

假设尚未成功更新：

```text
年龄 30 秒：缓存新鲜，直接返回。
年龄 70 秒：已过期 10 秒，可以先返回旧响应，同时后台验证或获取新响应。
年龄 100 秒：已过期 40 秒，超过 30 秒窗口，不能再单凭这条指令直接返回旧响应。
```

`30` 是过期后的额外时间，不是总新鲜期。后台更新通常由窗口内到来的请求触发，不是第 60 秒必定执行的定时任务。当前请求拿到旧内容后，缓存更新也不会自动把当前页面替换为新内容。

### 2.9 stale-if-error=N：上游故障时用过期副本兜底

```http
Cache-Control: max-age=60, stale-if-error=300
```

响应年龄为 120 秒时，已经过期 60 秒；此时访问上游遇到网络故障或 `500`、`502`、`503`、`504` 等错误，可以用旧的成功响应兜底。过期超过 300 秒后，不能再仅依据这条指令兜底。它不表示任意业务错误，例如 `404`，都能触发兜底。

`stale-while-revalidate` 解决后台更新期间的等待；`stale-if-error` 解决更新失败时的可用性。两者都需要缓存实现支持，并受其他明确限制约束。

### 2.10 其他指令与字段参数形式

#### no-transform：中间节点可以缓存，但不能擅自改内容

```http
Content-Type: image/jpeg
Cache-Control: public, max-age=600, no-transform
```

假设源站返回一张高清 JPEG，CDN 平时会把图片降低质量或转换成其他格式来减少流量。这里的 `no-transform` 要求 CDN 不要进行这样的内容变换，按源站提供的内容转发。它约束中间节点，即使该节点没有实现缓存，也受此限制。

它与“能否缓存”是两件事：这个例子仍允许浏览器、CDN 保存响应，600 秒新鲜期内可以按规则复用；只是不能为了优化传输而擅自改变图片内容。[规范说明](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.6)

#### must-understand：理解这个状态码的缓存规则，才允许存

这里的“理解”指理解并实现**响应状态码对应的缓存规则**，不是仅仅认识 `Cache-Control` 里的指令名称。

例如 `206 Partial Content` 表示响应只有文件的一部分。缓存需要知道如何保存、复用局部内容，不能把收到的片段当成完整文件返回。

```http
HTTP/1.1 206 Partial Content
Content-Range: bytes 0-99/1000
ETag: "file-v1"
Cache-Control: max-age=600, must-understand, no-store
```

这个例子返回文件的第 0～99 字节，完整文件共 1000 字节。两类缓存的处理不同：

- 不支持 `must-understand`：忽略不认识的指令，但仍认识 `no-store`，所以不保存。
- 支持 `must-understand`，并且理解、实现了这个状态码的缓存规则：规范建议忽略组合中的 `no-store`，在满足其他缓存条件时按局部响应的规则保存；600 秒是这里给出的新鲜期。

所以这组指令表达的是：“具备对应能力的缓存可以按规则存；不具备能力的缓存走不存储的兜底。”它不强制缓存必须保存，也不是“让所有节点都理解所有指令”。[规范说明](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.3)

#### private="字段名"：只禁止共享缓存保存指定响应头

`private` 禁止共享缓存保存整份响应；带字段名时，只禁止保存指定的**响应头**，正文及其余部分仍可按规则缓存。

```http
Cache-Control: max-age=600, private="X-User-Info"
X-User-Info: user-a
Content-Type: text/html
```

假设正文是所有人相同的公开文章，支持这种写法的 CDN 处理如下：

```text
源站发给用户 A：文章正文 + X-User-Info: user-a
CDN 保存的副本：文章正文及其余响应头，不保存 X-User-Info
之后发给用户 B：缓存的文章及其余响应头，没有 X-User-Info
```

用户 A 首次收到的响应仍包含这个头；只是 CDN 保存副本时不能存它，A 的浏览器仍可按规则保存完整响应。[规范说明](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.7)

#### no-cache="字段名"：指定响应头不能未经验证就再次发出

```http
Cache-Control: max-age=600, no-cache="X-Stock-Count"
X-Stock-Count: 10
Content-Type: text/html
```

假设正文是商品的固定介绍，自定义响应头 `X-Stock-Count` 表示库存数量。这里允许保存响应，但不希望后续请求未经验证就拿到旧的库存头。

支持这种写法的缓存，在 600 秒新鲜期内有两种处理方式：

- 直接复用介绍正文，但从返回的响应中去掉 `X-Stock-Count`，不能直接把旧的库存 10 发出去。
- 如果要保留这个头，就先向源站成功验证，并按验证结果更新或移除相应响应头，再返回响应。

它**不要求禁止存储这个头**；它限制的是后续复用响应时，这个头能不能未经验证就再次发出。这正是它和 `private="字段名"` 的区别。

| 写法 | 限制什么 | 能否不验证就复用正文 |
| --- | --- | --- |
| `no-cache` | 整份响应复用前必须验证 | 不可以 |
| `no-cache="X-Stock-Count"` | 指定头不能未经验证就复用；可以去掉该头后返回其余内容 | 其他规则允许时可以 |
| `private` | 共享缓存不能保存整份响应 | 共享缓存不能依靠这份响应建立缓存副本 |
| `private="X-User-Info"` | 共享缓存不能保存指定头，其余部分可按规则保存 | 其他规则允许时可以 |

这里带字段名的两种形式都不是普遍实现的能力。有些缓存会把 `private="..."` 当成整份响应的 `private`，把 `no-cache="..."` 当成整份响应的 `no-cache`，采取更严格的处理；不能假定所有浏览器和 CDN 都会精细到单个响应头。[规范说明](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)

参考：[Cache-Control 指令说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Cache-Control)、[HTTP 缓存规范](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2)、[过期响应扩展](https://www.rfc-editor.org/rfc/rfc5861.html)、[immutable 规范](https://www.rfc-editor.org/rfc/rfc8246.html)。

## 3. 请求指令：客户端表达本次要求

请求和响应的指令是单向的；请求带 `no-cache`，不代表响应也自动带 `no-cache`。RFC 9111 将请求指令定义为缓存可以支持的建议，不能假定每个中间节点都会遵循。

**不是“浏览器一定支持全部指令，中间节点都要开发者自己写”。浏览器已经内置 HTTP 缓存处理；CDN、Nginx 的缓存模块等也已有相应能力，开发者通常负责启用和配置，而非从头实现。只有自己开发缓存代理时，才需要自行或通过库实现这些行为。具体支持哪些指令、是否有覆盖规则，要看所用实现和配置。**[Nginx 缓存模块文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cache)

还要区分方向：响应中的标准缓存指令规定缓存必须遵守的限制；请求中的指令表达客户端对本次请求的要求，RFC 允许缓存选择是否支持。因此，浏览器发出请求头 `Cache-Control: no-cache`，不能据此保证整个链路的每个缓存节点都会向源站验证。

| 请求指令         | 意思                             | 例子                                         |
| ---------------- | -------------------------------- | -------------------------------------------- |
| `no-cache`       | 希望复用前先向源服务器成功验证   | 已有新鲜副本，也希望先验证                   |
| `no-store`       | 要求不保存本次请求和响应         | 不等于清空、绕过已有副本                     |
| `max-age=60`     | 希望响应年龄不超过 60 秒         | 已有副本年龄 120 秒，不符合要求              |
| `min-fresh=30`   | 希望至少还剩 30 秒新鲜期         | 只剩 10 秒新鲜期，不符合要求                 |
| `max-stale=120`  | 接受过期不超过 120 秒的响应      | 仍不能越过响应中明确禁止使用过期副本的限制   |
| `max-stale`      | 不指定过期时长上限               | 仍然受其他限制约束                           |
| `only-if-cached` | 只接受符合约束的缓存，不访问上游 | 遵循该指令的缓存无可用副本时，通常返回 `504` |
| `no-transform`   | 要求中间节点不要变换内容         | 不希望代理降低图片质量                       |

### max-stale=120 和 max-stale 有什么区别？

**带数值是限制“允许过期多久”，不带数值是不设置过期时长上限。这个时间从响应过期时开始算，不是从响应生成时开始算。**

假设已有响应的新鲜期为 60 秒：

```http
Cache-Control: max-age=60
```

下面假设缓存支持请求中的 `max-stale`，仍保留着这个副本，而且响应没有明确禁止使用过期副本：

| 当前响应年龄 | 已过期多久 | 请求带 `max-stale=120` | 请求带 `max-stale` |
| --- | --- | --- | --- |
| 100 秒 | 40 秒 | 接受，过期时长未超过 120 秒 | 接受 |
| 300 秒 | 240 秒 | 不接受，过期时长已超过 120 秒 | 接受，不限制过期时长 |

`max-stale=120` 相当于客户端说：“旧一点可以，但最多过期两分钟。”`max-stale` 则是：“只要其他规则允许，过期多久都可以。”

这只是客户端愿意接受旧副本，不会让响应重新变新鲜，也不会让缓存永久保存它。副本已经被删除，就没有缓存可用；如果响应带 `must-revalidate`，过期后必须成功验证，也不能因为客户端带了 `max-stale` 就直接返回旧副本。

参考：[请求指令规范](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.1)。

## 4. 多个指令一起出现，以谁为准？

指令的书写顺序不影响结果。处理组合时，分两种情况。

第一种是**同一件事有明确的覆盖关系**。例如决定新鲜期：

```http
Cache-Control: max-age=60, s-maxage=600
```

浏览器使用 `max-age=60`；CDN 使用 `s-maxage=600`。这是专门给共享缓存设置的覆盖规则，不是“取更小的值”。存在有效的 `max-age` 时，`Expires` 不再决定新鲜期。

第二种是**不同指令分别提出限制，需要一起满足**：

```http
Cache-Control: max-age=600, no-cache
```

`max-age` 给出 600 秒新鲜期，但 `no-cache` 额外要求“每次复用前验证”。因此即使只过去 10 秒，也不能直接使用，仍须验证。

```http
Cache-Control: max-age=600, must-revalidate
```

这次只要求“过期后必须验证”，所以前 600 秒可以直接使用，过期后再验证。

```http
Cache-Control: public, max-age=600, no-store
```

在这个组合中，`no-store` 禁止保存响应，前面的存储许可和新鲜期就无法用于后续缓存复用。

所以，**先看是否允许存，再看能保持新鲜多久，最后看复用前是否必须验证**；不能背成一条所有指令通用的优先级。[规范依据](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.2.1)

## 5. 普通刷新和强制刷新有什么区别？

**普通刷新不会把页面里的所有资源都拿去验证。以 Chrome 为例：HTML 主文档通常会重新验证；JS、CSS、图片等子资源，仍分别按照自己的缓存策略处理。**[Chromium 说明](https://blog.chromium.org/2017/01/reload-reloaded-faster-and-leaner-page_26.html)

一个页面的 HTML、JS、CSS、图片是不同的 HTTP 资源，各自有自己的响应头和缓存副本。刷新页面会重新加载页面所需资源，但“重新加载”不代表每份资源都要发网络请求。

例如，点击普通刷新时：

| 资源 | 已有缓存情况 | 如何处理 |
| --- | --- | --- |
| HTML 主文档 | `max-age=600`，只过去 30 秒，有 `ETag` | 通常仍会发条件请求验证；没变返回 `304`，变了返回 `200` 和新正文 |
| JS 文件 | `max-age=3600`，尚未过期 | 可以直接使用本地缓存，不发网络请求 |
| CSS 文件 | `no-cache`，有 `ETag` | 复用前需要发条件请求验证；没变返回 `304` |
| 图片 | `no-store`，没有可用缓存副本 | 重新请求并下载图片 |

如果某个子资源已经过期，且没有允许使用过期副本的规则，也通常需要验证；有验证器时可以发条件请求，没有可用验证条件时则重新获取完整响应。**不能把“普通刷新 HTML 通常会验证”扩大成“普通刷新所有资源都会验证”。**

下面只用 **HTML 主文档**，对比普通访问、普通刷新和强制刷新。假设浏览器已经保存了这份 HTML：

```http
Cache-Control: max-age=600
ETag: "v1"
```

现在只过去了 30 秒：

| 操作 | 浏览器怎样处理这份 HTML |
| --- | --- |
| 普通访问 | 缓存还新鲜，可以直接用，不发网络请求 |
| 普通刷新 | 通常带着 `"v1"` 去验证；没变则返回 `304`，继续用本地正文；变了则返回 `200` 和新正文 |
| 强制刷新 | 通常跳过本地缓存读取，也不附带本地缓存的版本条件，重新获取完整正文 |

普通刷新 HTML 相当于：

```http
Cache-Control: max-age=0
If-None-Match: "v1"
```

意思是：“这次先确认我保存的 v1 还能不能用。”**即使这份 HTML 缓存没有过期，也可以提前验证；这不代表它引用的 JS、CSS、图片都使用同样的请求方式。**

强制刷新通常会绕过本地 HTTP 缓存读取来重新获取 HTML 及其加载的子资源。请求中通常会带：

```http
Cache-Control: no-cache
```

并且不附带本地缓存生成的 `If-None-Match`。所以成功获取时，即使内容没变，通常也会重新传输完整正文。

注意：**区别不只在 `max-age=0` 与 `no-cache`，还在于是否读取本地副本、是否携带验证条件。**`no-cache` 本身并不禁止 `304`。

两种刷新都可以按新响应的规则保存缓存。强制刷新不等于禁止缓存，也不等于清空 CDN。不同浏览器的具体处理可能不同，上面的主文档与子资源区别以 Chrome 的行为为例。[刷新说明](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching#reload_and_force_reload)
