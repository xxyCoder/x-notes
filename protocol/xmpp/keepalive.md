# XMPP 心跳与断线

## 服务端内部逻辑分层（概念模型；非网络分层，具体取决于服务器实现）

1. **XML解析层**：接收字节流，解析XML；识别流顶层元素`<r/>`、`<a/>`、`<stream:error>`；将stanza向上交付。
2. **流管理模块(SM)**：处理`<r/>`/`<a/>`，维护h序列号。
3. **XMPP业务核心层**：处理`<iq>` `<message>` `<presence>`；完成路由、插件分发、业务逻辑（ping插件、消息投递、在线状态）。

> 
> 关键区分（典型实现的划分，XEP 未规定 `<r/>`/`<a/>` 的处理层级）：`<r/>`/`<a/>`属于流顶层控制元素，不进入业务核心层；iq/message/presence才会流入业务核心层。

## 一、两类断线（协议视角）

1. **显式断线（有明确信号，无需心跳）**

- 收到`</stream:stream>`：优雅关闭
- 收到`<stream:error> + </stream:stream>`：流异常终止
> 直接判定会话结束。

2. **静默逻辑断线（心跳解决的核心场景）**
无任何流关闭信号；XML解析仍在等待标签，但远端XMPP实体不再处理stanza。
> RFC6120核心协议没有原生报文检测该状态，必须依赖扩展。

## 二、基础概念：保活 vs 探活

- **保活 keep-alive**：周期发包，避免中间网关回收空闲会话；单向输出，不需要应答。
- **探活 detect dead**：验证对端 XMPP 实体/路径能对 IQ 及时应答（只证明该实体响应，不证明消息队列、路由插件等业务全部正常）；**必须具备强制应答契约**，超时即按本地策略判定连接不可用。

> 
> 心跳不会制造断线，仅做检测器，识别已死亡流；不负责重连、会话恢复。

## 三、三种保活/探测手段

### 1. Whitespace keepalive（流空格，RFC6120）

- 直接向XML流输出空格，不属于stanza。
- ✅ 保活（维持NAT会话）；RFC6120 §4.6.1 也把发空格列为**检查底层 TCP 连通性**的常用方法——写失败/传输层超时仍能暴露死连接。
- ❌ 无XMPP层应答契约，**不能独立完成应用层探活**；本地写成功不等于远端实体仍在处理stanza。

### 2. XEP-0199 XMPP Ping（标准应用层心跳）

> 
> 依托RFC6120 IQ强制契约：`iq type="get/set"` MUST返回 result / error。

合法ping请求（示例 ping 服务器本体，to=域 JID；ping 账号/组件则填对应 JID；省略 to=本服务器直处理）

```
<iq id="p1" type="get" to="demo.com">
  <ping xmlns="urn:xmpp:ping"/>
</iq>
```

合法pong应答（`result`允许无子节点；服务器代表自身应答时 `from` 必须为服务器域名，RFC6120 §8.1.2.1 规则2）

```
<iq from="demo.com" to="alice@demo.com/pc" id="p1" type="result"/>
```

（`to` 可省略——服务器自产 stanza 的 to 应为客户端 full JID 或不带；`from` 不可省）

规则：

1. `iq type="get"`必须携带`<ping/>`命名空间子节点；裸`iq get`（无/多子元素）违反RFC6120 §8.2.3规则5，RFC未明确定义此种情况的应答，**通常**返回 `type="modify"` + `bad-request` 的 **stanza error**（流不关）——xmpp.js iqCallee 的实现即 `<iq type="error"><error type="modify"><bad-request/></error></iq>`。
2. 发出ping，开启超时计时器，严格匹配iq的id。
3. 收到对应id的result/error → 流存活。
4. 超时无匹配id应答 → 按本地策略判定连接不可用（静默逻辑断线）。
5. 收到任意业务stanza(message/presence/iq)，可推迟ping发送，减少报文（客户端调度策略，非 XEP-0199 规则）。

- 能力：同时支持**保活 + 探活**。
- 兜底（协议合规行为）：支持 ping 回 result，不支持回 iq-error（XEP-0199 §3）；现实中的故障或错误实现仍可能无响应，超时判定不可省。

### 3. XEP-0198 流管理 `<r/> / <a/>`

- **定位**：业务stanza累计确认、断线后会话恢复resume；**不是通用探活心跳**。
- **扩展前提**：SM为可选扩展，必须完成握手：客户端发`<enable>`，服务端回复`<enabled>`，SM会话正式开启。
- **协议契约**
  - 已开启SM：收到`<r/>` MUST回复`<a h="N"/>`（XEP-0198 §4 Acks）。
  - 未开启SM：XEP-0198 **没有规定**收到`<r/>`的行为——属实现自定义（忽略或关流都可能；若回`<failed/>`属**非标准用法**：§6 只为`<enable/>`/`<resume/>`的错误定义了`<failed/>`，另只说“滥用SM MAY终止流”）。xmpp.js 中间件对SM命名空间`<r/>`不检查enabled状态一律回`<a/>`。“静默丢弃”只是部分实现行为，不能当协议契约。
- **机制特点**
  - 累计确认模型，**无事务ID**。
  - `h`：对端**已处理 stanza 的累计数量**（数值上等于最后一条已处理 stanza 的序号，XEP-0198 §4）。**unsignedInt 32 位计数：超过 2³²-1 后 SHALL 回绕到 0**（§4 原文，不能当永久递增序号）。handled = **已接受责任**（已送达客户端/已路由），不保证业务层处理完成——这正是下面“假在线”问题的根源之一。
  - **每个 `<r/>` 都必须回一个 `<a/>`**（XEP-0198 §4：MUST acknowledge it by sending an `<a/>`，且应答 SHOULD 尽快、MUST NOT 被扣住不发；xmpp.js 对每个 `<r/>` 各调一次 sendAck()）。"一个 `<a h="N"/>` 覆盖多条 stanza"指的是**stanza 的累计确认**，不是多个 `<r/>` 可合并应答。
- **不建议作为标准探活心跳的3个原因**（XEP-0198 §1 也建议用 whitespace / XEP-0199 ping / TCP keepalive 做连通性检查）
  1. 累计确认无事务ID绑定：`<a/>`无法像 IQ 那样无歧义匹配并发的多个 `<r/>`；但若实现**串行化**（同一时刻只保留一个未应答 `<r/>`），可对"本次 `<r/>` → 下一个 `<a/>`"设等待超时——这是由"每个 `<r/>` 必获 `<a/>`"推导的**可行实现**，不是协议提供的 ID 配对机制。"任意入站元素即重置计时器"只是 xmpp.js 0.14.0 的实现选择。
  2. 仅校验底层，不校验业务核心层：`<r/>`/`<a/>`只经过XML解析层、流管理模块，**不进入业务核心层**（架构风险推理，非 XEP-0198 定义；h 何时+1 取决于各实现对“已处理/已接受责任”的认定，分层并非所有服务器的固定架构）。业务线程死锁、队列打满的故障场景下，底层仍可以正常返回`<a/>`，可能产生**假在线**。
  3. 依赖扩展握手，无全局兜底：未开启SM时行为未定义（见上）；不像IQ拥有RFC强制的应答兜底规则。

> 
> 工程用途：SM开启后，`<r/>`可以替代whitespace空格做流保活（XEP-0198 §8.2）。
> 注意“禁止用于静默断线判定”说得太死：xmpp.js（0.14.0）实现就是周期性发`<r/>`做连接检查（源码注释 "Periodically send r to check the connection"，默认约30秒一次），60秒无任何入站元素即断开——`<r/>`+粗粒度超时判死可行（xmpp.js 即如此实现），只是要清楚它只覆盖流/SM层（概念模型）、无单次探测配对语义。

## 四、逻辑判定流程

```
流状态
├─收到 </stream:stream> / stream-error → 直接判定断线，无需心跳
└─无关闭信号
   ├─空闲超时 → 发送XEP-0199 ping，启动超时计时器
   │   ├─收到匹配id result/error → 存活，重置计时器
   │   └─超时无应答 → 按本地策略判定连接不可用（静默逻辑断线）
   └─收到任意stanza → 证明近期有入站活动，可推迟下一次ping（不证明出站方向/应答链路/业务队列正常，不能替代匹配id的ping探测）
```
