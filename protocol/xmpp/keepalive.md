# XMPP 心跳与断线

## 服务端内部逻辑分层（概念模型；非网络分层，具体取决于服务器实现）

1. **XML解析层**：接收字节流，解析XML；识别流顶层元素`<r/>`、`<a/>`、`<stream:error>`；将 stanza 向上交付。
2. **流管理模块(SM)**：处理`<r/>`/`<a/>`，维护 h 序列号。
3. **XMPP业务核心层**：处理`<iq>` `<message>` `<presence>`；完成路由、插件分发、业务逻辑（ping 插件、消息投递、在线状态）。

> 
> 关键区分（典型实现的划分，XEP 未规定 `<r/>`/`<a/>` 的处理层级）：`<r/>`/`<a/>`属于流顶层控制元素，不进入业务核心层；iq / message / presence 才会流入业务核心层。

## 一、两类断线（协议视角）

1. **显式断线（有明确信号，无需心跳）**

- 收到 `</stream:stream>`：优雅关闭
- 收到 `<stream:error> + </stream:stream>`：流异常终止
> 直接判定会话结束。

2. **静默逻辑断线（心跳解决的核心场景）**
无任何流关闭信号；XML解析仍在等待标签，但远端XMPP实体不再处理stanza。
> RFC6120核心协议没有原生报文检测该状态，必须依赖扩展。

## 二、基础概念：保活 vs 探活

- **保活 keep-alive**：周期发包，避免中间网关回收空闲会话；单向输出，不需要应答。
- **探活 detect dead**：验证对端 XMPP 实体/路径能对 IQ 及时应答（只证明该实体响应，不证明消息队列、路由插件等业务全部正常）；**必须具备强制应答契约**，超时即按本地策略判定连接不可用。

> 
> 心跳不会制造断线，仅做检测器，识别已死亡流；不负责重连、会话恢复。

## 三、三种保活/探测手段

### 1. Whitespace keepalive（流空格，RFC6120）

- 直接向 XML 流输出空格，不属于 stanza。
- ✅ 保活（维持NAT会话）；RFC6120 §4.6.1 也把发空格列为**检查底层 TCP 连通性**的常用方法——写失败/传输层超时仍能暴露死连接。
- ❌ 无 XMPP 层应答契约，**不能独立完成应用层探活**；本地写成功不等于远端实体仍在处理 stanza。

### 2. XEP-0199 XMPP Ping（标准应用层心跳）

> 
> 依托RFC6120 IQ强制契约：`iq type="get/set"` MUST返回 result / error。

合法 ping 请求（示例 ping 服务器本体，to=域 JID；ping 账号/组件则填对应 JID；省略 to=本服务器直处理）

```
<iq id="p1" type="get" to="demo.com">
  <ping xmlns="urn:xmpp:ping"/>
</iq>
```

合法pong应答（`result` 允许无子节点；服务器代表自身应答时 `from` 必须为服务器域名，RFC6120 §8.1.2.1 规则2）

```
<iq from="demo.com" to="alice@demo.com/pc" id="p1" type="result"/>
```

（`to` 可省略——服务器自产 stanza 的 to 应为客户端 full JID 或不带；`from` 不可省）

规则：

1. `iq type="get"`必须携带`<ping/>`命名空间子节点；
2. 发出 ping，开启超时计时器，严格匹配 iq 的 id。
3. 收到对应 id 的 result/error → 流存活。
4. 超时无匹配 id 应答 → 按本地策略判定连接不可用（静默逻辑断线）。
5. 收到任意业务 stanza(message/presence/iq)，可推迟 ping 发送，减少报文（客户端调度策略，非 XEP-0199 规则）。

- 能力：同时支持**保活 + 探活**。
- 兜底（协议合规行为）：支持 ping 回 result，不支持回 iq-error（XEP-0199 §3）；现实中的故障或错误实现仍可能无响应，超时判定不可省。

### 3. XEP-0198 流管理 `<r/> / <a/>`

用途：确认业务 stanza、支持断线后的 session resume。SM 是可选扩展，客户端发送 `<enable>`、服务端回复 `<enabled>` 后才生效；它不是通用探活协议。

确认规则：

- SM 已启用：每个 `<r/>` 都必须得到一个 `<a h="N"/>`；应答 SHOULD 尽快发送，MUST NOT 故意扣留（XEP-0198 §4）。一个 `<a/>` 可以累计确认多条 stanza，但不能用一个 `<a/>` 合并应答多个 `<r/>`。
- SM 未启用：XEP-0198 没有规定如何处理 `<r/>`，实现可以忽略或关流。此时回复 `<failed/>` 不是标准行为；`<failed/>` 只用于 `<enable/>` / `<resume/>` 失败。xmpp.js 会直接回复 `<a/>`，这是实现选择，不是协议保证。

`h` 的含义：

- `h` 是对端已处理 stanza 的累计数量，不是事务 ID。
- “已处理”表示已经接受投递责任，例如已交给客户端或完成路由，不保证业务逻辑执行完成。
- `h` 是 32 位 `unsignedInt`，超过 2³²-1 后 SHALL 回绕到 0，不能当作永久递增序号（XEP-0198 §4）。

不适合作为通用探活的原因：

1. `<r/>` / `<a/>` 没有 ID，无法像 IQ ping 一样匹配并发探测。串行发送 `<r/>` 并等待下一个 `<a/>` 可以实现超时检测，但这是工程约束，不是协议的请求响应配对。
2. `<a/>` 只证明 SM 层接受了责任，不证明业务线程、队列或处理链正常。底层仍能回复时可能出现“假在线”；这是架构风险推理，不是 XEP-0198 定义的固定服务器分层。
3. 它依赖 SM 握手；未启用时没有统一行为。XEP-0198 §1 建议使用 whitespace、XEP-0199 ping 或 TCP keepalive 检查连通性。

工程上，SM 启用后可用 `<r/>` 代替 whitespace 做流保活（XEP-0198 §8.2），也可配合粗粒度超时发现静默断线。xmpp.js 0.14.0 会周期性发送 `<r/>`，并在约 60 秒没有任何入站元素时断开；“任意入站元素重置计时器”同样只是它的实现策略。

## 四、逻辑判定流程

```
流状态
├─收到 </stream:stream> / stream-error → 直接判定断线，无需心跳
└─无关闭信号
   ├─空闲超时 → 发送XEP-0199 ping，启动超时计时器
   │   ├─收到匹配id result/error → 存活，重置计时器
   │   └─超时无应答 → 按本地策略判定连接不可用（静默逻辑断线）
   └─收到任意stanza → 证明近期有入站活动，可推迟下一次ping（不证明出站方向/应答链路/业务队列正常，不能替代匹配id的ping探测）
```
